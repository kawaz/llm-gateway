# DR-0012: 転送のたびに起きたことをイベントとして配る

- Status: Active
- Date: 2026-08-01

## Context

prompt cache の有効期間 (5 分) は、**upstream が前処理を始めた時点**から走る。
残り時間を出したい外部の画面 (ccmsg の WebUI) から見ると、その時点は直接
観測できない。

gateway は全部のリクエストを仲介しているので、**upstream が応答ヘッダを
返した瞬間**を知っている唯一の場所になる。本文が流れ始める前なので、前処理が
終わった時刻に一番近い。ここを外へ知らせれば、見る側は会話ごとに 5 分を
数え直せる。

既にある口はどちらも「今の状態を聞きに来る」形で、この用途に向かない:

- `/llm-gateway/usage` (DR-0007) — credential ごとの枠。聞いた時点の値
- `/llm-gateway/stats` (DR-0011) — 日ごとの積算。転送 1 本の時刻を持たない

## Decision

### `GET /llm-gateway/events` を SSE で生やす

繋いでいる間、転送のたびに 1 通ずつ流す。

**SSE を選ぶ (WebSocket ではない)**:

- **依存が増えない**。axum は既に入っていて、`Sse` と `KeepAlive` が今の
  feature (`http1` / `json` / `tokio`) で使える。WebSocket は `ws` feature が
  要る
- **向きが片方だけで足りる**。流すのは gateway → 見る人の一方向で、見る側から
  送ってくるものが無い。双方向の口を開けると、使わない受信経路の面倒を見る
  ことになる
- **切れたときの繋ぎ直しを相手が持っている**。ブラウザの `EventSource` は
  自動で繋ぎ直す。WebSocket だと見る側が再接続を書く
- **中身が見える**。`curl` でそのまま読める形なので、動作確認に道具が要らない

### webhook へ POST する

gateway は設定した `base_url` のパスへ `/webhook/llm-gateway` を足した先へ
イベントを送る。`base_url` を書かなければ webhook 全体を無効にする。token を
別の宛先へ送らないよう、scheme は HTTP / HTTPS に限り、userinfo・query・fragment
を持つ値は起動時に拒否する。stable / unstable のように複数の gateway が同時に
動く構成でも、それぞれが同じ受け口へ送るため、受け手が特定の gateway へ接続し
続ける必要がない。SSE は `curl` による確認用として残す。

認証には `Authorization: Bearer <token>` を使う。token は設定値に直接書かず、
`token_file` の 1 行テキストから起動時に読む。既定は
`$XDG_DATA_HOME/ccmsg/webhook-llm-gateway.token` (`XDG_DATA_HOME` が無ければ
`~/.local/share/ccmsg/webhook-llm-gateway.token`)。読めない場合は warning を 1 回
記録して webhook だけを無効にし、転送は続ける。token の値と応答本文はログへ
出さない。

短時間に起きたイベントは 200 ms、最大 100 件の窓で配列にまとめる。高頻度時に
1 件ごとの接続を作らず、画面表示では判別できない遅延に収めるためである。JSON の
実バイト数でも分割し、1 通を 1 MB 以下にする。単独で 1 MB を超えるイベントはその
1 件だけを落として warning に残す。

**受け口は複数書ける** (`webhook.base_urls`)。書いた全部へ同じ知らせを流し、
gateway は宛先を選ばない — 会話の id は世界で一意で、受け取った側は自分の
知らない会話を捨てる。「どの受け口がその会話を持っているか」を gateway が
知る必要も、探す必要も無い (探せば、受け取る側の接続状態を gateway が
追い続けることになる)。1 つの受け口が落ちていても、他への配達は止めない。

送信は転送処理から切り離し、3 秒で timeout する。204 を受理として扱い、それ以外の
応答と通信失敗は warning に残す。再送と順序保証は行わない。連続失敗は最初の 1 回
だけ warning を出し、復帰時に失敗回数を記録する。

### 流すのは「起きたこと」だけ。状態は持たない

SSE の `data` と webhook の JSON 要素は同じ `Event` 型を使う。webhook は常に配列で
送る。

1 通の形 (欄の名前が、見る側との契約):

```
event: request
data: {"ts":1785600000,"ts_iso":"2026-08-01T12:00:00Z","session_id":"s-1",
       "ns":"personal","model":"claude-fable-5","credential":"claude-kawazzz",
       "status":200,"prefix":"2cf24dba","origin":"main","cache_ttl_secs":3600,
       "cache_expires_at":1785603600,"cache_expires_at_iso":"2026-08-01T13:00:00Z"}
```

- `ts` / `ts_iso` — **upstream へリクエストを送り始めた時刻**。5 分はここから
- `session_id` — リクエストヘッダ `X-Claude-Code-Session-Id` の値 (大文字
  小文字は問わない)。名乗らないクライアント (curl 等) では `null`。欄自体は
  必ず出す — 欠けさせると、読む側が形を 2 通り扱うことになる
- `ns` / `model` / `credential` — どの面の・どのモデルが・どの経路に当たったか。
  `model` は解決後の実名 (`opus` のような短い名前はここでは解決済み)
- `status` — upstream が返した状態
- `prefix` — **会話系列の識別子** (下記)。分からなければ欄ごと出さない
- `origin` — この 1 本を出した側 (`main` / `sub` / `unknown`)。見分け方は
  DR-0024。欄自体は必ず出す
- `cache_ttl_secs` — **この 1 本が残すプレフィックスの寿命** (秒)。効かせた
  戦略 (DR-0024) で決まり、本文に触らない場合は送った `cache_control` を読む
  (`ttl: "1h"` がひとつでもあれば 3600、`ttl` の無いブレークポイントだけなら
  300)。ブレークポイントが無ければ欄ごと出さない
- `cache_expires_at` / `cache_expires_at_iso` — `ts` + `cache_ttl_secs`。
  残りを数える側で足し算をさせない。寿命が分からなければ欄ごと出さない

`cache_ttl_secs` は `prefix` と同じ性格の値で、**キャッシュに当たる保証では
ない** — プレフィックスが変われば実際には効かない。リングが描けるのは
「この 1 本が置いた cache は、何も無ければいつまでもつか」まで。

**本文もトークン数も載せない**。何を書いたかは gateway も残していない
(DR-0011 と同じ姿勢) し、5 分を数えるのに要らない。

### 会話の id だけでは系列を分けられない

同じ会話の id で、**メインとサブエージェントの往復が混ざって飛ぶ**。両者は
別の system prompt を使うので、upstream の cache も別々に載る。id だけで
束ねると、サブエージェントの 1 本がメインの残り時間を巻き戻す。

`system` 配列の**先頭要素の `text`** を SHA-256 して、頭 8 桁を `prefix` に
入れる。先頭ブロックだけを見るのは実測 (451 リクエスト) の結果:

- **配列全体は不変ではない**。末尾ブロックに `git status` 由来の内容
  (コミット一覧・未コミットのファイル) が入っていて、リポジトリを触るたびに
  変わる。全体を見ると、同じ系列が作業のたびに別物へ分かれる
- **先頭ブロックは安定**。`x-anthropic-billing-header: cc_version=…` で始まる
  ブロックは、全リクエストで同じハッシュだった

**これは「同じ系列か」の印であって、キャッシュに当たる保証ではない。**
upstream の cache はプレフィックス全体の一致を要るので、`git status` で末尾が
変われば実際には効かない。`prefix` が同じでもキャッシュが無効になっていること
はある。リングが示すのは**その系列で最後にリクエストが飛んだ時刻**であって、
キャッシュの生死ではない。

取り方は `system/0/text` を 1 箇所引くだけ。本文は受け取り口で既に解釈済み
なので、**大きさに関わらず費用は変わらない** (ハッシュを取るのも先頭ブロック
だけ)。文字列で書かれた古い形式・空配列・`text` の無いブロックでは欄ごと
出さない — 読めないものを埋めない。

既存の欄は変えていない。`prefix` を知らない読み手はそのまま動く。

**断られた応答も流す**。経路を切り替えたときは、当たった先ごとに 1 通ずつ
出る (429 の後に 200、など)。どれを使うかは見る側が `status` で決められる。
こちらで「通った分だけ」に絞ると、上限に当たっている様子が外から見えなくなる。

### 見ている人がいなければ何もしない。遅れたら落とす

`tokio::sync::broadcast` で配る。

- **転送の邪魔をしない**のが第一。誰も見ていなければ送らず、配れなかったことを
  転送側へ持ち帰らない (待たない・失敗にしない)
- 溜めておけるのは 256 件。追いつけない見物人の分は**落とす**。5 分の残りを
  数える相手に、遅れて届いた開始時刻を渡しても使い道がない。落とした数は
  gateway 側のログに残す
- **過去には遡らない**。繋いだ時点で既に過ぎている分を配っても数え直せない

### 認証は掛けない。keepalive は 20 秒

usage / stats と同じ扱いで、手前の tailnet の境界を信頼する (DR-0006)。
載せるのは会話の id と経路の名前までで、本文は流れない。

`Access-Control-Allow-Origin: *` を付ける。主な相手はサーバ同士で話す
ccmsg だが、様子を見るのにブラウザから直接開けると早い。そもそも認証を
持たない口なので、生成元で絞っても守れるものは増えない。

何も起きない時間が続くと経路上の中継に切られるので、20 秒ごとに SSE の
コメント行を送る。

## Alternatives Considered

**WebSocket で双方向にする** — 見る側から絞り込み条件 (この会話だけ、等) を
送れる利点はあるが、今の用途は「全部を受けて手元で選ぶ」で足りる。絞り込みが
要るようになったら、query で受けて配る側で絞る方が、双方向の口を開けるより
影響が小さい。

**転送の応答ヘッダに時刻を足す** — 見る側がクライアントを兼ねている場合しか
使えない。ccmsg の WebUI は転送の当事者ではないので届かない。

**`/llm-gateway/stats` に時刻の列を足す** (DR-0011) — 積算の置き場に 1 本ごとの
時刻を混ぜることになる。あれは「日ごとにいくら使ったか」を答える形で、
1 本ごとの記録を持つと日次ファイルが際限なく伸びる。

**取りこぼしを無くす (確認応答つきで配る)** — 見物人が遅い時に転送を待たせる
ことになる。転送の速度を、見物人の都合で落とさない。
