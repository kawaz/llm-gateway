# DR-0019: 借りる枠は経過した時間ぶんまで (pace_cap)

- Status: Accepted
- Date: 2026-08-16

## 背景

個人の面から仕事用の credential を借りたい。ただし**貸す側のペースには絶対に
食い込まない**のが条件で、貸してよいのは「仕事側がまだ使っていない遅れ分」
だけになる。

枠は「窓の期間で使い切ってよい量」であって「いつ使ってもよい量」ではない。
7d 窓の頭で一気に使えば、残りの 6 日は貸し手が自分の枠を使えない。逆に言うと、
**経過した時間の割合までしか使わない**なら、貸し手が按分どおりに使う限り
ぶつからない。借り手は按分線の下だけを通る。

DR-0018 (spend_down) とは向きが逆になる:

| | DR-0018 spend_down | DR-0019 pace_cap |
|---|---|---|
| 見るもの | 窓の**終端** (リセットが近いか) | 窓の**途中** (按分線を超えたか) |
| すること | 蒸発する前に余りを刈る | 按分線の下だけ貸す |
| 効き方 | 候補の**順序**を変える | 候補に**なるか**を決める |

同じ Snapshot (最長周期枠の window_seconds / reset / utilization) を入力に
するが、片方は順序、もう片方はフィルタなので衝突しない。

## 決定

### 1. `routes` の要素を、名前でも table でも書けるようにする

```toml
[[ns.personal.routing]]
models = ["claude-fable-*"]
routes = [
    "codex-kawaz",
    { route = "codex-emrd", pace_cap = { ratio = "100%", step = "12h" } },
    # 同格グループの中でも同じように書ける
    ["a", { route = "b", pace_cap = { ratio = "80%" } }],
]
```

DR-0015 が「グループ位置に table も書ける形を後から**追加**すればよい」と
残した枠をそのまま使う。文字列・配列・table は形が重ならないので、既存の
書き方は 1 文字も直さずに読める。

**同格グループの中の要素にも書ける**。個人面の claude 系は同格グループが
主な形なので、外側の要素だけでは使えない。

`pace_cap` は **route 1 本ごと**の属性で、同じ経路でも規則が違えば
(= モデル群ごと、namespace ごとに) 別の上限を書ける。

### 2. 予算は経過を階段に下ろして測る

```
経過   = 窓長 - (リセット時刻 - 現在)     (窓開始 = リセット時刻 - 窓長)
段数   = floor(経過 / step)
予算   = (段数 × step / 窓長) × ratio
```

**使用率 ≤ 予算なら候補、超えていれば除外**。

- `ratio` は `"0%"`〜`"100%"` の割合文字列 (既定 `"100%"`)。**按分線を超える値は
  書けない** — この上限は貸し手のペースに食い込まないためのもので、先食いを
  許す方向は目的に反する。`"80%"` のように手前で締める方向だけ意味がある
- `step` は `spend_down_within` と同じ書式 (`"12h"` / `"10%"`)。既定は窓長の
  1/14 で、7d 枠なら 12 時間

設定に出てくる割合はすべて `"N%"` の文字列にしてある。素の小数と混在すると、
読むたびに単位を確かめることになる。

### 3. 上限に達したら、次の段の境界まで控える

次に予算が増える時刻は `窓開始 + (現段 + 1) × step` で決定的に計算できる。
これを `until` に載せた断り (`Reason::Paced`) の形で表し、`select` が候補から
外す。全滅すれば既存の 429 組み立て (DR-0009 / DR-0014 §8) がそのまま動き、
クライアントは無駄な再試行をしなくて済む。

`Reason` に新しい語を足すのは、これが **upstream に断られたのではなく自主的な
抑制**だから。様子を聞きに行っても状況は変わらない、という違いが語彙に出る。

**判定は経路の状態ではなく `Route` の上で行い、印は残さない**。上限は
namespace × モデル群ごとに違うので、経路 (`RouteState`) に印を置くと面を
またいで効く — 借り手の面で締めた上限が、貸し手の面まで止めてしまう。
`Route` は 1 リクエストぶんの組み立て結果なので、書いた規則のとおりにだけ
効く。upstream へ当てずに手前で外すだけなので、印を残さなくても無駄打ちは
起きない。

### 4. 見るのは最長周期の枠だけ

DR-0018 §2 と同じ。5h 窓は数時間で回るので、そこに借用の概念が無い。窓の
選び方 (`window_seconds` が大きい方) も DR-0018 と共有する。

utilization の観測遅延は**段の粗さに吸収させる**。12 時間刻みに対して観測の
遅れは桁が違うので、補正を足しても精度は上がらず、判定だけが複雑になる。

### 5. 判定できないなら貸さない

窓長・リセット時刻・使用率のどれかが読めない経路は、**上限を書いた経路に
限り**候補から外す (書いていない経路は従来どおり)。貸し手の枠を守るのが目的
なので、安全側は締める方。

### 6. 鶏卵を切るため、判定の前に枠を聞く

「通さないと応答ヘッダが読めない → 読めないから通さない」で永久に閉じる。
そこで上限つきの経路の枠が読めていないときは、**判定の前に**枠照会 API を
叩いて埋める。枠照会はトークンを消費しない (DR-0007) ので、待つ価値がある。

- 聞いた答えは、使える窓を持たない経路に限ってスナップショットに写す。
  **あるものは上書きしない** — ヘッダと枠照会は同じ枠に違う値を返すことが
  あり (DR-0007 実測)、転送のたびに更新されるヘッダ側の方が新しい
- 写すときに読むのは `model` の付かない枠 (= 経路全体に掛かるもの) だけ。
  モデル別の枠は経路全体の消費を表さない。この選り分けは `QuotaLimit` の欄で
  できるので、core は provider 固有の分類を知らないままでいられる
  (DR-0014 §3)。`kind` → 周期の対応表は preset の中 (DR-0018 §6 と同じ場所)
- 枠照会 API を持たない provider の経路に上限を書いた場合は、スナップショット
  頼みになる。それでも読めなければ §5 のとおり外れる
- 聞きに行くのは札 (`claim_ask`) を取れたときだけなので、答えない相手に毎
  リクエスト当たり続けることはない

### 7. 保護を最後まで通すか、使い切りに明け渡すかは経路ごとに選ぶ

`pace_cap` に `spend_down_release`(既定 `false`) を足す。`true` にすると、
同じ規則の `spend_down_within` (DR-0018) の窓に入った時点で階段を解放し、
リセットまでに残りを使い切らせる。

credential ごとにリセットの曜日が違うので、望みが割れる:

- **週末に回る credential**: 貸し手はその時間帯に使わない。余りを残す意味が
  無いので、使い切りに入ったら解放してよい (`true`)
- **営業時間中に回る共有 credential**: 貸し手がリセット直前まで使う可能性が
  ある。最終段も含めて食い尽くさない (`false`)

段は `floor` で数えるので、**既定では最終段の端数が解放されないまま
リセットで蒸発する**。これは取りこぼしではなく**保護そのもの**で、貸し手の
ために空けてある余白にあたる (`ratio = "100%"`、既定の刻みなら窓長の 1/14)。
借り手が最後の一滴まで飲まないことが、この機能の目的だった。

既定を `false` にするのは、保護が安全側だから。書き忘れが「うっかり
使い切る」方向に転ばない。

### 8. spend_down との順序 — フィルタが先

`pace_cap` は「候補になるか」、`spend_down` は「候補の順序」。**上限で外れる
経路は、使い切りの繰り上げ対象にもしない**。使えない経路を先頭へ寄せても
順序が 1 つ無駄になるだけで、後ろの経路の相対順は変わらない。

## 採らなかった案

- **連続 (非階段) cap**: 予算を経過そのもの (連続値) にすると、上限際の経路が
  「秒ごとにわずかな予算が増えては即座に使い切る」を繰り返す。細切れに許可が
  出るたびに 1 本通してすぐ cap に戻るので、**貼り付いた状態で無駄な消費だけが
  進む** (kawaz 裁定)。段にすれば、開いた瞬間にまとまった予算があり、次に開く
  時刻も先に言える
- **`ratio` に 100 % 超を許す**: 借り手が貸し手のペースへ食い込む。この機能の
  目的そのものに反する
- **`ratio` を素の小数 (`1.0`) で書く**: 設定内に `"25%"` と `1.0` が混在し、
  読むたびに単位を確かめることになる
- **上限を経路の状態 (`RouteState`) の印として控える**: 断りの印は経路の
  持ち物なので namespace をまたいで効く。「個人面では按分線で締めるが、
  仕事面では素通し」が書けなくなり、借り手のために付けた印が貸し手の面まで
  止める — 機能の前提そのものが壊れる。控えて得られるのは upstream への
  無駄打ちの削減だが、それは手前で候補から外す時点で既に起きていない
- **`spend_down_release` を規則全体の設定にする**: リセット曜日は credential
  ごとに違うので、同じ規則の中で「解放してよい相手」と「最後まで守る相手」が
  混ざる。route ごとに選べないと、どちらかに寄せるしかなくなる
- **最終段の端数を既定で解放する**: 書き忘れが「うっかり使い切る」方向に
  転ぶ。守るために付ける設定なので、既定は守る側に置く
- **枠が読めない経路を通す**: 上限を「読めたときだけの努力目標」に格下げする
  ことになる。貸し手の枠は守れない
- **枠を裏で聞いて次のリクエストに回す**: その 1 本は判定できないまま外れる。
  枠照会はトークンを消費しないので、待って正しく判定する方がよい
- **枠照会の答えでスナップショットを常に上書きする**: 同時刻に 7d 枠がヘッダ
  では 0.34、枠照会では 100 という実測 (DR-0007) がある
- **観測遅延を補正する**: 段の粗さ (既定 12 時間) に対して遅延は桁が違う。
  補正を足しても精度は上がらず、判定の説明だけが難しくなる
