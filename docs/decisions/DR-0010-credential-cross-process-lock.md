# DR-0010: 認証情報の書き換えを `.lock` サイドカーの flock でプロセス間排他する

- Status: Active
- Date: 2026-07-29

## Context

同じ credential ディレクトリを複数のプロセス (別ポートで並走する gateway、CLI)
が共有している。OAuth の refresh token はワンタイムなので、同時に更新に走ると
片方が焼かれる。

commit `ee91d2fc` でディスクの読み直しを入れたが、それは「相手が**完了済み**」を
検知する仕組みで、同時突入は素通りする。調査 (docs/findings/2026-07-29-credential-store-concurrency.md)
で残っていたのは 4 つ。

- **窓 A**: `do_refresh` の読み直しから POST までの間に相手も POST し、片方が
  `invalid_grant` で失敗する
- **窓 B**: 断られた側の回復のための読み直しが、成功した側の書き込みより先に走る。
  1 回きりで待たないので、そのまま失敗として返る
- **窓 C**: `do_refresh` の書き込みは読み直した時点のスナップショット由来なので、
  POST の最中に他プロセスが書いた denied_beta を丸ごと消す (lost update)。
  `record_denied_beta` との間で同一プロセス内でも起きる
- **控えの陳腐化**: cache は access token の期限が切れるまでディスクを見ない。
  他プロセスの更新・denied_beta の学習・手で直した priority が最大 8 時間反映
  されない

加えて、一時ファイルの名前が `<id>.json.tmp` 固定で、2 プロセスが同時に書くと
同じファイルを切り詰め合い、混ざった JSON が rename されうる。

## Decision

### 排他の単位は credential 1 つ、口は `<id>.json.lock` への flock

認証情報そのものではなく、脇に置いた `.lock` ファイルを掴む。本体を掴めない
のは、書き換えが rename だから。掴んだファイルは rename の瞬間に古い中身の
ほうへ取り残され、後から来た相手は新しいファイルを掴んで素通りする。名前が
動かない脇のファイルなら、全員が同じ 1 つを待つ。

**`.lock` は消さない**。掃除のつもりで消して作り直すと、既に掴んでいる側と
後から来た側が別のファイルを見ることになり、本体を掴んだときと同じ理由で
締め出しが破れる。中身は空で大きさも増えないので、置いたままにする。

排他の口は `Persistence` trait に置く (`type Guard` / `fn lock`)。置き場を
差し替えれば排他の実装も入れ替わり、試験では中身の見える偽物を使える。
`FileStore` が flock、試験用の置き場はプロセス内の Mutex や無操作。

依存は **rustix (fs feature)** を直に使う。すでに tempfile 経由で
依存グラフに居る。`fd-lock` はプラットフォーム差を吸ってくれるが、
guard がロック本体を借りる形なので「取った権利を持ち回る」用途では
自己参照になり収まらない。rustix の `flock` は開いたファイルをそのまま
権利として持てる。

Windows では `rustix::fs::flock` が無くコンパイルが通らない。無操作で
すり抜ける実装を置くより、排他が無い環境ではビルドが止まるほうがよい
(この gateway は launchd 常駐と codesign を前提にしていて、対象は macOS)。

### ロック区間は「読み直しから書き込みまで」の 3 か所

- `do_refresh`: 冒頭の読み直しの**前**に取り、保存と控えの入れ替えまで持つ。
  権利を得た時点の読み直しがそのまま二度目の確認になり、相手が済ませていれば
  更新に入らない (窓 A と窓 B が同時に閉じる)
- `record_denied_beta`: 同じく読み直しの前から保存まで (窓 C と、プロセス内の
  lost update)
- CLI の login の保存: 認可が通った後、土台を読み直してから書き終えるまで。
  再ログインするのは refresh token が失効したときで、その裏では常駐している側が
  同じ認証情報の更新を試している。土台を読むのはロックを取った後にする
  (ブラウザを開く前に読んだ内容を土台にすると、待っている数分の間に相手が
  覚えた denied_beta を消す)

プロセス内の束ね (`in_flight`) はそのまま。ロックまで来るのは 1 プロセスに
つき 1 本なので、束ねとロックは二重にならない。束ねの Mutex を持ったまま
ロックを取りに行かない (取るのは束ねの外)。

待ちはブロックするので `spawn_blocking` へ逃がし、権利は RAII で返す
(落とせば外れる)。flock の待ちは相手が手放した時点で起きるので、様子を
見に行く必要がない。

### 控えは版と一緒に持ち、読み出しのたびに版を照合する

控えの 1 件に「読んだ時点の版」を添える。`acquire` の入口の読み出しで版を
見比べ、変わっていれば読み直す。`FileStore` の版は更新時刻 (`fs::metadata`
の mtime)。書き換えは rename なので、中身が入れ替われば必ず動く。

前提として、mtime がナノ秒まで刻まれること (APFS / ext4) に頼っている。
秒までしか持たない置き場では、同じ秒の中で 2 回書かれると版が動かず、
後の書き込みを見落とす。

読み直しでは**版を先に**読む。読んだ後に版を見ると、読み終えてから書かれた
中身を「今の版」として覚えてしまい、その更新に気づけない。逆の順なら、
取りこぼしても次の読み出しで食い違って読み直しになる。自分で書いたときだけは
書き込みの後に版を読む (権利を持っている間なので割り込まれない)。

版が取れない置き場は `None` を返してよい。`None` 同士は「変わっていない」と
みなす = 控えをそのまま使う。

### 一時ファイルの名前に書き手を混ぜる

`<id>.json.tmp.<pid>` にする。rename の原子性はそのまま。同じプロセスの中の
2 者は上のロックで直列化されるので、プロセス単位で分ければ足りる。

### やらないこと

- **再試行・待ち直しのループは入れない**。待つのは flock の役目で、そこに
  秒数を足しても根拠のない数字が増えるだけ
- **ロックを取れないときに素通りさせない**。取得の失敗はそのままエラーにする。
  「排他できないが動く」状態は、壊れ方が読めなくなる
- **「更新後に旧 access token が無効化されるか」の実機確認はしない**。
  元 issue の受け入れ条件 2 はこれを確認する話だったが、確認したかった害
  (陳腐化した access token を期限まで使い続ける) は版の照合で構造ごと消える。
  他プロセスが更新すれば版が動き、次の読み出しで新しい token に乗り換わる。
  upstream がどちらの実装でも結果は変わらない

## Alternatives Considered

**認証情報の本体ファイルを flock する** — 脇のファイルが 1 つ増えないのは利点
だが、rename で inode が変わるので排他が破れる。書き換えの前後で別のファイルを
掴んだ 2 者が、互いに排他していると思い込んだまま同時に走る。

**`try_lock` + backoff で待つ** — 取れなかったときの待ち時間に根拠がない。
短くすれば無駄に起きて、長くすれば更新が遅れる。flock のブロッキングは
相手が手放した瞬間に起きるので、待ち方として上位互換。

**排他を入れず、読み直しの回数を増やす** — 窓が狭くなるだけで閉じない。
更新は HTTP の往復ぶん (数百 ms) 開いたままなので、期限切れが同時刻に成立する
構図 (`keep_models_fresh` が全 credential を一斉に触る) では実際に重なる。

**プロセス内の束ね (`in_flight`) をロックで置き換える** — 束ねは「待っている
全員に同じ結果を配る」仕組みで、ロックは「順番に通す」仕組み。置き換えると、
同じプロセスの 8 本が順番にロックを取り直し、そのたびに読み直しが走る。
役割が違うので両方置く。
