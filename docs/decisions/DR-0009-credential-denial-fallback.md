# DR-0009: この経路に断られた応答 (401/403/429/529) は次の経路へ回す

- Status: Active
- Date: 2026-07-29

## Context

複数の認証情報を並べていても、上限に当たった 1 つでリクエストが終わっていた。

切り替えの条件は `should_try_next` = `500 | 502..=504` だけで、429 はそのまま
クライアントへ返っていた。理由として「レート制限は別の経路でも同じように当たる
可能性が高く、切り替えると単に負荷が移るだけ」と書いてあった。これは **1 つの
アカウントを複数のレプリカで分け合う構図**の理屈で、この gateway の構図とは違う。
ここに並ぶ認証情報は**別のアカウント**で、上限もトークンの有効性もアカウント単位に
付く。片方が上限に当たっていることは、もう片方が使えないことを意味しない。

401 も同じ扱いになっていた。refresh token が失効した認証情報が 1 つあるだけで、
まだ生きている認証情報を試さずにクライアントへ 401 が返る。

もう 1 つ、経路の記憶 (affinity) にも 2 つの穴があった。

- `forward()` は `accept_or_switch` が `Ok` を返した応答すべてで `remember()` を
  呼んでいた。429 や 401 も `Ok` なので、**断られた経路に会話が貼り付く**。次の
  転送も同じ先から始まる
- affinity の鍵が会話だけで、namespace を見ていなかった。会話の鍵は本文と一部の
  ヘッダから derive するので、**別の namespace へ同じ本文を投げると鍵が一致する**。
  片方の面で覚えた順が、もう片方の面の経路の順を書き換える

## Decision

### 401 / 403 / 429 / 529 は「この経路に断られた」とみなし、次の経路を試す

`is_route_denial(status) = matches!(status, 401 | 403 | 429 | 529)` を
`should_try_next` と並べて置く。`should_try_next` (経路断) は変えない。
2 つの違いは応答を持ち回るかどうかで、こちらは捨てずに抱える。

- **429**: 上限はアカウント単位。別のアカウントなら余っている
- **401 / 403**: upstream との認証の話。クライアント側の認証は namespace の
  トークンで gateway が別に検めているので、ここまで来た 401 は「gateway が
  出した認証情報が通らなかった」以外の意味を持たない
- **529**: 混み具合は**宛先ごと**に付く。ここに並ぶ経路は認証情報が別なだけで
  なく宛先も分かれている (Bedrock / api.anthropic.com / 中継) ので、片方が
  詰まっていることは、もう片方が詰まっていることを意味しない。
  実測 (2026-07-29 07:15): Bedrock 経路が同じモデルに 529 を返し続けている
  間、OAuth 経路の同じモデルは 200 を返していた

### 全部断られたら、最後に見た応答をそのまま返す

`try_route` は断られた応答を**捨てずに**呼び出し側へ渡す。`forward()` は最後の
1 つを持っておき、経路を使い切ったらそれをクライアントへ返す。

`Error::AllUpstreamsFailed` (= 503) に化けさせない。429 の応答には `retry-after` や
上限のリセット時刻が載っていて、**クライアントはそれを見て次の一手を決める**。
503 に置き換えると、その手掛かりが消えたうえで「upstream が落ちている」という
別の事実を伝えることになる。401 も同じで、「認証を直せ」が「落ちている」に化ける。

経路断 (5xx) と混ざった場合は、断られた応答が残る。5xx は応答を持ち回らないので
上書きされない。どれも断られなかった (全部 5xx / 接続不能) なら従来どおり
`AllUpstreamsFailed`。

本文はストリームのまま抱える (buffer しない)。断られた応答は小さく、後続を
試している間コネクションを 1 本握っていてもコストに見合う。

### 断られた経路は、期限まで候補から外す

切り替えだけでは、上限に当たった認証情報が先頭にいる限り**すべての
リクエストが毎回そこに当たる**。1 本あたり 1 往復ぶんの遅れが、窓が開く
まで乗り続ける。gateway は応答ヘッダから上限の状態とリセット時刻を読んで
いる (DR-0007) のに、経路を選ぶ側がそれを見ていない。

断られた経路に「いつまで断られているか」の印を付け、その間は候補から
外す。**空ける長さと効かせる範囲を、断られ方で変える**:

| 断られ方 | いつまで | 効く範囲 | 様子を聞きに行くか |
|---|---|---|---|
| 429 + 塞がっている窓 (5h / 7d) | その窓が開く時刻まで | credential 全体 | 行く (下記) |
| 429 で窓が読めない | `retry-after`、無ければ 60 秒 | 頼んだモデルだけ | 行かない |
| 529 (混雑) | `retry-after`、無ければ 60 秒 | 頼んだモデルだけ | 行かない |
| 401 / 403 | 印を付けない | — | — |

**上限 (429 + 窓)** は、いつ開くかが応答に書いてある。開く時刻を知って
いるのだから、そこまでは実リクエストで一度も選ばない。窓が複数塞がって
いるなら最も近い開く時刻まで (5 時間の窓が埋まっていても 7 日の窓に余裕が
あるなら、5 時間の方で開く)。**上限を頭打ちにはしない** — 開く時刻を
知っていながら早めに当てに行っても、429 を貰い直すだけになる。

窓が塞がっているかは、通っている側の語 (`allowed`, `allowed_warning`) を
数えて判定する。語彙は公式に記載が無く増えうる (DR-0007) ので、知らない語
で締め出しを見送ると印が付かないまま元の毎回 429 に戻る。

**混雑 (529)、および窓を伴わない 429** は、いつ空くかを誰も知らない。
短く退避して様子を見るだけにする。これを窓つきの 429 と同じに扱うと、
空いている経路を根拠なく長時間閉じる。

### 締め出しの範囲は、応答が示した証拠の広さに合わせる

同じ認証情報でも、**あるモデルだけ断られる**ことが実際にある。認証情報
ごと締め出すと、使えるはずの経路を自分で閉じる。

実測 (2026-07-31、同じ認証情報に数秒差で問い合わせ):

| 頼んだモデル | 状態 | 上限のヘッダ | 本文 |
|---|---|---|---|
| haiku-4-5 | 200 | 5h `allowed` (0.14) / 7d `allowed` (0.07) | — |
| fable-5 | 429 | **1 つも載らない** (`x-should-retry: true` のみ) | `{"type":"rate_limit_error","message":"Error"}` |
| opus-5 | 429 | 同上 | 同上 |
| sonnet-5 | 429 | 同上 | 同上 |

**モデル別の制限は、応答ヘッダのどこにも現れない。** 窓は 5h / 7d の 2 つ
だけで、どちらも `allowed` のまま、特定のモデルだけが 429 になる。断られた
モデルを知る手段は「何を頼んだか」しかない。

そこで、範囲は**応答が示した証拠の広さ**で決める:

- 窓が塞がっているという証拠がある (429 + rejected な窓) → 窓はアカウントに
  掛かるので、**その credential の全モデル**を締め出す
- 証拠が無い (窓を伴わない 429 / 529) → **頼んだモデルだけ**を締め出す。
  他のモデルまで止める根拠が応答のどこにも無い

2xx が返ったら、そのモデルの印と credential 全体の印の両方を消す。通った
という事実は、どちらの印も間違いだったことを示す。

窓の名前 (`5h` / `7d` の別) では鍵を分けない。分ける意味が出るのは
「モデル別の窓」が現れたときだが、上の実測のとおり今は現れない。現れたら
[`Scope`] にその窓を足し、影響するモデルの範囲へ効かせる。

401 / 403 には印を付けない。時間が経っても直らないので、待つ意味がない。
リクエストの中で次の経路へ回すところまでは今までどおり。

2xx が返った経路の印は消す。

**どれも断られているなら、どこにも当てずに 429 を返す**。最も近い開く時刻を
`retry-after` に載せる。開く時刻を知っていながら当てに行くのは、分かって
いる壁にぶつかりに行くのと同じで、クライアントを待たせるだけ増える。

印はメモリだけに持つ。落として失うのは再起動直後の 1 回の空振りで、その
1 回が印を付け直す。ディスクに置くと、もう空いている経路を古い印で締め出す
方向の間違いが増える。

### 上限で締め出した経路には、裏で様子を聞きに行く

リセット時刻は「遅くともここまでには開く」であって、それより早く開くことも
ある。実リクエストを当てない以上、聞きに行かなければ開いたことに気づけない。

締め出し中の経路に **1 時間おき**、一番安いモデル (haiku) へ `max_tokens = 1`
のリクエストを 1 本投げ、返るヘッダで今の状態を見る。開いていれば印を外して
経路に戻し、まだ塞がっていれば開く時刻を控え直す。

- **実リクエストが流れているときだけ**聞きに行く。転送の中で役を立てるので、
  誰もそのモデルを使っていない間は 1 本も投げない。締め出しに気づく人が
  いないのに実費だけ払うのは無駄
- **聞き終わるのは待たない**。要求から切り離した仕事として走らせ、結果は
  次のリクエストが使う。この 1 本を遅くしてまで待つ価値はない
- 聞きに行く役の札は [`Drop`] で外す。走り切っても途中で落ちても同じ道を
  通す (認証情報の更新と同じ形、DR-0010)。走り切った経路だけで外すと、
  落ちたときにその経路へ二度と聞きに行けなくなる
- **混雑には聞きに行かない**。開く時刻を持たないので短い退避で足り、
  聞くだけ実費が増える
- 上限のヘッダを返すのは Anthropic のサブスクだけ (DR-0007)。他の種類の
  認証情報には聞きに行かない — 聞いても今の状態が読めない
- 聞きに行った分のトークンは日次集計に積む (DR-0011)。gateway が自分の
  都合で使った分でも実費なので隠さない

利用状況の定期的な取り直しから印を作ることはしない。応答を受けたときと、
聞きに行ったときだけにして、観測の経路を絞る。

### gateway では retry-after 待ちの再送をしない

上限に当たったとき、`retry-after` の秒数だけ待って同じ経路へ投げ直す手もあるが、
採らない。gateway が待つと、その間リクエストが滞留してコネクションとメモリを
握り続ける。手前のプロキシから見ると単に応答が遅い相手になり、そちらの
タイムアウトを誘発する。待つ判断はクライアント側のバックオフに委ねる。
gateway がやるべきなのは「今すぐ使える経路があるなら使う」ことだけ。

### 覚えるのは 2xx だけ

`forward()` は `resp.status / 100 == 2` のときだけ `remember()` を呼ぶ。断られた
応答を透過して返す場合も覚えない。affinity は「この経路で通った」を残すもので、
「この経路を試した」ではない。

### affinity の鍵を (namespace 名, 会話) にする

会話の鍵だけでは namespace 間で衝突する。`Namespace` は自身の名前を持たない
(設定では `[ns.<名前>]` のキー) ので、`forward` / `routes_for` / `remember` に
名前を引数で渡す。名前を `Namespace` に持たせる案は採らない — 設定を読み書きする
構造体に、実行時の都合だけの項目を足すことになる。

## Alternatives Considered

**429 だけ次へ回し、401 は透過する** — 失効した認証情報 1 つで、生きている
残りが使われないままになる。実際に起きた事象がこれ。

**全滅時に `AllUpstreamsFailed` (503) を返す** — 上で書いたとおり、クライアントの
リトライの意味論が壊れる。エラーの一覧としては丁寧だが、機械が読む相手に対しては
状態コードを保つほうが情報量が多い。

**断られた応答を buffer してから次へ行く** — 本文を読む必要がない。読むと
その分だけ遅くなり、返すときに組み立て直す手間も増える。さらに、**本文の
到着が滞ると buffer 待ちがフォールバックそのものを塞ぐ**。抱えたまま進む
方式なら、本文がいつ届くかに関わらず次の経路の試行はすぐ始まる。

**最初に断られた応答を返す** — どれを返しても大差ないが、最後のものにすると
「全部試した末の状態」になる。順番の意味 (優先度の低い経路ほど後) からも、
最後に見たものが現時点の最新の観測。

## 関連

- Caddy (手前のプロキシ) は 429 を受けても upstream を切り離さない設定にしている。
  あれは**同じ認証情報に向いた複数レプリカ**の間で負荷を分ける話で、切り離すと
  残りに負荷が寄るだけなので正しい。本 DR は**別アカウントの認証情報をまたぐ**
  切り替えで、軸が違う。両立する
- [DR-0003](./DR-0003-beta-flag-negotiation.md) — 400 を受けて beta を落とし
  送り直す仕組み。断られた beta の学習は認証情報単位で、本 DR の切り替えより
  内側 (1 経路の中) で起きる
- [DR-0007](./DR-0007-usage-visibility.md) — 上限のヘッダを通りすがりに読む
  仕組み。締め出す期限はここで読んだ窓の状態とリセット時刻から決める。
  応答に載る窓は 5h / 7d の 2 つで、モデル別の窓は載らない (上の実測)。
  モデル別の制限は「頼んだモデルが 429 で返る」形でしか観測できないので、
  範囲の判定もそこから起こしている
- [DR-0006](./DR-0006-namespace-routing.md) — namespace の単位。affinity を
  namespace で分けるのはこの単位に揃えるため
- [DR-0008](./DR-0008-user-facing-language.md) — 新規の error message は英語
