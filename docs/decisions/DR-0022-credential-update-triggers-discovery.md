# DR-0022: 認証情報の更新を版で見張り、一覧を即座に取り直す

- Status: Accepted
- Date: 2026-08-26

## 背景

2026-08-26、2 本の Claude OAuth credential の refresh token が同時に失効した。
discovery が 401 で落ち、その route のモデルが catalog から消えた。残った route は
枠を使い切っており、failover 先が無いまま 429 が返り続けた。

`llm-gateway login` で認証情報を入れ直すと、token 自体は稼働中の daemon にも届く。
控えは版 (mtime) の照合で鮮度を保つので、次に読むときに置き場から読み直される
(DR-0010)。しかし **catalog は別**で、`discovery.refresh_secs` (既定 1 時間) の
周回まで組み直されない。実際にはこの周回を待てず、daemon を再起動して回復させた。

つまり「認証情報を直したのに、モデルが戻らない」時間が最大 1 時間ある。障害の最中に
一番効く操作 (= login) の効果が見えないので、利用者は再起動という強い手に出る。

## 決定

### 1. 検知は置き場の版のポーリング。login からの通知にはしない

`llm-gateway login` が稼働中の daemon へ HTTP で知らせる案は採らない。同じ
credentials ディレクトリを**複数の daemon が共有**している (安定版と検証版など)。
通知は 1 台にしか届かず、届かなかった側は元の問題を抱えたままになる。置き場を
見張る側に置けば、その置き場を使う daemon が全部気づく。

版は DR-0010 が既に持っているもの (`Persistence::version`、`FileStore` では
mtime のナノ秒) をそのまま使う。中身は読まない — 読むと期限を見て refresh token を
使う判断まで巻き込むので、「変わったか」だけを見る。

### 2. 見張りは既存の周回に相乗りする

新しい待ち合わせのループは足さない。`keep_models_fresh` の刻みを
`discovery.watch_secs` (既定 60 秒) に細かくし、毎周で 2 つを判断する。

- 見張っている版のどれかが変わった → その場で取り直す
- 変わっていなくても `discovery.refresh_secs` ぶん経った → 従来どおり取り直す

見張る先は **一覧を聞きに行く route の credential だけ**。聞きに行かない route
(relay 型) の認証情報は catalog に影響しないので、混ぜると無関係な更新で取り直す。

### 3. 取り直すのは catalog 全体。変わった credential だけに絞らない

`Router::refresh` は全 route を 1 度に組み直す作りで、取れなかった route は前回の
結果を残す。1 本ぶんだけ差し替える口を新設するより、そのまま呼ぶほうが状態が 1 つで
済む。問い合わせは route の本数ぶんで、頻度も更新のあった時だけなので、upstream への
負荷は無視できる。

daemon 自身の token 更新でファイルを書いた場合も、同じ経路で 1 回取り直しが走る。
無駄ではあるが害は無く、書いたのが自分か他人かを見分ける仕掛けを足すほうが高くつく。

## 影響

- `[discovery] watch_secs` を追加 (既定 60)。省略できるので既存の設定はそのまま動く
- 版を持たない置き場では従来どおり `refresh_secs` の周回だけで取り直す
- login 側は変更なし。認証情報を書けば、その置き場を見ている daemon が全部追従する
