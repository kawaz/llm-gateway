# DR-0013: 設定は `extends` で土台の上に重ねる

- Status: Active
- Date: 2026-08-01

## Context

同じ内容の設定を 2 つ持っている。待ち受け先だけが違う 2 台
(`config-stable.toml` / `config-unstable.toml`) で、**listen の行以外を手で
一致させる**運用になっている。

credential を 1 つ足す、routing の順を変える、といった変更のたびに同じ編集を
2 回する。片方を直し忘れると、どちらの gateway に当たったかで挙動が変わる。
気づくのは「片方だけ動かない」と分かってからで、原因に辿り着くまでが遠い。

## Decision

### `extends = "パス"` で土台を指す

書いたファイルは、指した設定を**土台**にして、自分に書いた分で上書きする。

```toml
# config-unstable.toml
extends = "config-shared.toml"

[server]
listen = "127.0.0.1:8402"
```

**`include` ではなく `extends`。** `include` は「その位置に貼り込む」印象を
与えるが、TOML のキーには順序の意味が無い。ファイルの先頭に書いても末尾に
書いても結果は同じで、位置に意味を持たせられない。**位置に依存しない語**を
選ぶ。`extends` なら「これを土台にする」だけを言い、どこに書くかの話をしない。

### 表は鍵ごとに潜り、それ以外は丸ごと置き換える

覚えることを 1 つにする。

- **表 (テーブル)** — 鍵ごとに潜って重ねる。`credentials.bedrock.exclude` だけ
  書けば、`type` と `url` は土台のまま残る
- **それ以外 (数・文字列・真偽・配列)** — 丸ごと置き換える

**配列を要素ごとに混ぜない。** 経路の優先順 (`routing` / `credentials`) は
**並びそのものが意味**なので、混ぜると派生側が書いた順に土台の要素が割り込む。
「どこに入るか」を予想しながら書く設定にはしたくない。書いたなら書いたとおりに
なる。除外パターン (`exclude`) も同じで、狭めたつもりが土台の分だけ広いまま、
という読み違いを生まない。

### 消す手段は用意しない

土台の項目を派生側から取り除く書き方 (`!key` のような否定) は持たない。
消したいなら土台を直すか、意味の無い値で塗り潰す。

否定を入れると、**設定を読むたびに「どこかの派生ファイルがこれを消している
かもしれない」を疑う**ことになる。畳んだ結果を確かめる手段 (`llm-gateway check`)
はあるが、原文を読んで分かる状態のほうが良い。

### 相対パスは、それを書いたファイルの隣から

`extends` に相対パスを書いたら、**そのファイルの位置**から解く。起動時の
作業ディレクトリは見ない。設定ファイルの意味が、どこから起動したかで変わって
はいけない (launchd から起動するか手元の shell から起動するかで、読む土台が
変わる状態を作らない)。

### 何段でも重ねられる。循環はその場で止める

深さは制限しない。段を増やすかどうかは設定の都合で、こちらが決める理由がない。

循環 (自分自身 / A→B→A) は**読み込みが戻ってこない**ので、辿ったファイルを
実体で覚えておいて検出する。`./a.toml` と `a.toml` と symlink 越しの同じ
ファイルを別物と数えると見逃すので、パスは正規化してから見る。

指した先が無ければ、**どのファイルがどのパスを指したか**を言う。指された側の
名前だけ出しても、複数段あるときにどこを直せばよいか分からない。

### 土台だけを置いた設定は、待ち受けない

`--config` を省いて CLI (`llm-gateway usage` / `stats`) を使いたい。既定の
`config.toml` に土台を指す設定を置けば、問い合わせ先を毎回打たずに済む。

```toml
# config.toml — CLI から使うためだけの設定
extends = "config-common.toml"

[server]
disabled = true
listen = "127.0.0.1:11300"
```

`disabled = true` の設定で `serve` を始めると、既に動いている面と待ち受け先を
取り合う。**始めようとした時点でエラーにする** — 黙って何もせずに終わると、
起動したつもりのまま「繋がらない」原因を探すことになる。`check` は通し、
待ち受け行に無効だと出す (設定として壊れてはいない)。

**`listen` の意味は変えない。** 「どこで待つか」ではなく**「この面がどこに
いるか」**を書いた欄として、CLI の問い合わせ先の組み立てには使い続ける。
待ち受けない設定に住所を書くのは一見ちぐはぐだが、CLI がやりたいのは
「あの面に聞く」であって、聞き先を別の欄で二重に持つほうが分かりにくい。

## Alternatives Considered

**`include` にする** — 上記のとおり、位置に意味があるように読める。実際には
位置非依存なので、語と挙動が食い違う。

**配列も要素ごとに混ぜる** — routing の優先順が壊れる。「土台の後ろに足す」
規則にしても、先頭に入れたい場合の書き方が別に要る。

**複数の土台を並べられるようにする** (`extends = ["a", "b"]`) — 重ねる順の
規則が増え、同じ鍵を 2 つの土台が持つ場合の勝ち負けを覚えることになる。
1 本の鎖なら「手前が勝つ」だけで済む。要るようになってから足せる。

**設定を 1 ファイルに戻し、待ち受け先を環境変数で渡す** — listen だけなら
足りるが、次に「片方だけ credential を外したい」が来ると環境変数が増える。
設定の差分は設定で表す。

**CLI の問い合わせ先に別の欄を作る** (`[client] url = …`) — 待ち受けない設定に
`listen` を書く違和感は消えるが、住所を書く欄が 2 つになる。どちらを直せば
よいかを覚えることになるので、`listen` 1 つで通す。
