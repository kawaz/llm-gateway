# DR-0036: 低優先度で送られた 1 本は、429 / 529 で経路を替えずにクライアントへ返す

- Status: Accepted (kawaz 裁定 2026-10-06)
- Date: 2026-10-06

## 背景

Claude Code の `/low-priority` は、通常の枠 (5h) の壁に当たった後も、遅くてよければ作業を続けられる機能。request に `anthropic-usage-limit: slow` を付けると subscription の低優先度枠で送られ、週の枠を消費する (UI 文言「Continue now at lower priority (uses your weekly limit)」)。低優先度で使える量にも週の上限がある。

低優先度枠の上流は、混んでいる 1 本を 429 (`slot_busy`) / 529 で返し、待つ長さと理由を応答ヘッダ `anthropic-ratelimit-unified-slow-{offer,status,retry-after,max-wait,budget-utilization}` に載せる。Claude Code はそれを読んで**自分で待ち、同じ 1 本を送り直す** (既定で約 20 秒 ± 30 %、上限約 20 分、`retry-after` / `max-wait` に従う)。`weekly_limit` / `budget_exhausted` / `ineligible` / `off` では中断する (Claude Code v2.1.282 の binary 解析、`docs/findings/2026-09-25-claude-code-low-priority.md`)。

DR-0009 は 429 / 529 を「この経路に断られた」とみなして即座に次の経路へ回し、断った経路に印を付けて候補から外す。低優先度の 1 本にこれを当てると 2 つ壊れる:

- **待てば通る 1 本で、別のアカウントの枠を使う**。本人が待つと選んだ 1 本を、gateway が勝手に別の subscription へ流す
- **印が積もると、次の 1 本は gateway が組んだ 429 になる** (DR-0009 の「どれも断られているなら、どこにも当てずに 429 を返す」)。この 429 には低優先度のヘッダが無く、Claude Code の待機が働かない。通常の枠で全経路が締め出された後こそ `/low-priority` の出番なので、機能そのものが gateway 越しに使えなくなる

もう 1 つ、DR-0019 (pace_cap) は借りる枠を経過時間ぶんに抑える。低優先度の 1 本は、本人が週の枠の前借りを選んで送っているので、gateway が重ねて抑えると二重の制限になる。

## 決定

### 1. 見分けるのは request のヘッダ

`anthropic-usage-limit: slow` (名前・値とも大文字小文字を問わない) を付けた 1 本を**低優先度**として扱う。読むのは入口 (`session::low_priority`) で、core (`gateway.rs` / `router.rs`) は「クライアントが断りを自分で待つ 1 本か」の 1 bit だけを持つ (DR-0014 §3)。

応答のヘッダ (`…-slow-status`) では判定しない。529 には低優先度のヘッダが載らないことがあり (`active` または欠落でクライアントは待つ)、応答で判定すると透過すべき 529 で経路を替えることになる。

### 2. 429 / 529 は経路を替えず、そのまま返す

低優先度の 1 本が 429 / 529 を受けたら、**次の経路を試さず、その応答をヘッダごとクライアントへ返す**。待つ判断はクライアントに任せる (DR-0009 の「gateway では retry-after 待ちの再送をしない」と同じ構え)。

- **印を付けない** (DR-0009 の締め出しを通さない)。低優先度枠の混み具合は、通常の優先度の経路が使えるかを示さない
- **2xx でも印を外さない**。上限に当たった後も通るのが低優先度枠なので、通ったことは通常の優先度の上限が開いた証拠にならない。印の付け外しは通常の優先度の観測だけで行う
- 経路の結びつき (affinity) は従来どおり 2xx で覚える。会話の prompt cache を同じ経路に保つためで、結びつきは並び順を決めるだけなので、通常の優先度の 1 本は印の付いた経路をこれまでどおり外す
- 透過した 529 は upstream の状態 (DR-0021) で failing にしない。低優先度枠の混み具合で、上流の障害とは限らない。429 は届いた証拠として数える (DR-0021 §2)

### 3. 印で全部塞がっていても、こちらで 429 を組まない

経路を選ぶとき (`Router::select`)、低優先度の 1 本は:

- **使える経路があれば、通常の 1 本と同じ選び方をする** (印の付いた経路を外し、外した理由を `skipped` に載せる)。低優先度だからといって、通常の 1 本より悪い先へは送らない — 例えば 1 本目の経路の週の枠が尽きていて 2 本目が空いているとき、1 本目に貼り付けると低優先度枠の `weekly_limit` で中断するだけになる
- **全部が上限・混雑の印で塞がっていたら、429 を組まずに印の付いた経路を設定順のまま当てる**。上流が答えた断りには待つためのヘッダが載る。当てた経路は `skipped` に載せない (外していない)
- **組織ごとの断り (`org_not_allowed`) だけは優先度に依らず外す**。待っても直らず、低優先度枠も同じ組織の利用になる。全部が組織ごとに断られていれば、通常どおり gateway が 429 を組む

### 4. 消費の上限 (DR-0019) に掛けない

低優先度の 1 本は `pace_cap` で外さない。上限の判定に要る枠の照会 (DR-0019 §6) も待たない。

### 5. 待っても直らない断りと経路断は、従来どおり次へ回す

401 / 403 (認証) と 5xx (経路断) は優先度に依らず DR-0009 のまま次の経路へ回す。死んだ credential や落ちた宛先は、待っても通らない。

### 6. `slot_busy` 以外の低優先度の状態も、同じく透過する

上流が 429 で返す低優先度の状態は `slot_busy` のほかに `weekly_limit` / `budget_exhausted` / `ineligible` / `off` がある。gateway は status で判定する (§1) ので、これらも**すべて経路を替えずに返す**。

- `weekly_limit` / `budget_exhausted`: 低優先度の週の枠を使い切った。別の経路へ回すと、本人が選んでいない別の subscription の枠を黙って使う。クライアントは中断して本人に知らせるので、続けるか (低優先度を外して通常の優先度で送る等) は本人が決める
- `ineligible` / `off`: この経路では低優先度枠が使えない。別の経路なら使えることもありうるが、どの経路なら使えるかを gateway は知らない。替えて試すと、通常の優先度の断りと区別の付かない応答を経路の数だけ集めることになる。中断させて本人に見せる方を取る
- 低優先度のヘッダを伴わない 429 (低優先度枠を持たない経路の通常の上限など) も同じく透過する。クライアントは通常の 429 として扱って待つ

迷う所は透過に倒している。替える方へ倒すと、裁定の趣旨 (本人の待機を邪魔しない、別の subscription を勝手に消費しない) を外したときの害が大きく、透過で外したときの害はクライアントが中断して本人に見えるだけで済む。

### 7. events には低優先度の印だけを載せる

転送の知らせ (`request`、DR-0012) に `low_priority: true` を載せる。当てはまらない 1 本では欄ごと出さない。低優先度の 1 本は 429 / 529 でも経路を替えないので、断りが並んでも経路が尽きたとは限らない。それを見る側が区別できるようにする。gateway がヘッダを記録しないので、`/low-priority` が gateway 越しに実際に効いているかを外から確かめる口もこれになる。

応答側の低優先度の状態 (`offer` / `status` 等) は載せない。値の語彙は公式に記載が無く、gateway はそれで振る舞いを変えない (§1)。

## 採らなかった案

- **切り替えはするが、切り替え先にも低優先度で送り、全滅時は低優先度のヘッダ付きの最後の応答を必ず返す**: 待てば通った 1 本で別の subscription の枠を使う問題がそのまま残る。また、前の 1 本が付けた印で全経路が塞がる (§3 の問題) のは同じで、そこに別の手当てが要る
- **応答の `…-slow-status` で判定する**: 529 は低優先度のヘッダを伴わないことがある (§1)。判定に方言の語彙を core へ持ち込むことにもなる
- **低優先度の 1 本は印を全部無視して設定順に当てる**: 1 本目の週の枠が尽きている (印あり) とき、2 本目が空いていても 1 本目の `weekly_limit` で中断する。通常の 1 本なら 2 本目で通っていた。使える経路がある間は通常どおり選ぶ方 (§3) が、低優先度を付けたことで悪くならない
- **低優先度で通った 2xx で印を外す**: 通常の優先度の上限が開いた証拠にならない (§2)。外すと次の通常の 1 本が 1 往復を捨てて印を付け直す
- **`weekly_limit` / `budget_exhausted` / `ineligible` / `off` では次の経路へ回す**: §6
- **低優先度の 1 本も pace_cap に掛ける**: 本人が週の枠の前借りを選んでいるので、二重の制限になる (kawaz 裁定)

## 未確認

- 実 request の観測。`/low-priority` は feature gate の対象ユーザーで、かつ通常の枠の壁に当たっていないと使えない (`-p` では使えない)。gateway 越しの送信条件 (非 streaming で pathname の末尾が `/v1/messages`) は binary 解析では真で、§7 の印で実際に届いているかを確かめられる
- 課金 (表示は「uses your weekly limit」まで)。低優先度の消費が `anthropic-ratelimit-unified-7d-*` のどれに出るかは見ていない
