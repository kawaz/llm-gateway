# DR-0037: ns 認証 `jwt` の鍵を gateway 自身が入れ替え、helper から呼ぶ発行コマンド `auth token` を持つ

- Status: Accepted (kawaz 裁定 2026-10-06)
- Date: 2026-10-06

## 背景

`jwt` の namespace (DR-0030 §6) は、手で作った鍵 (`keys_file`) で長寿命の token を鋳造して配り、ローテも手で行う形で始まった。Claude Code の `apiKeyHelper` を使えば、token を都度発行して短寿命にできる (`docs/findings/2026-10-06-api-key-helper.md`)。Claude Code は JWT の `exp - 30s` を過ぎると helper を同期で呼び直し、401 / 403 でも呼び直す。裏の呼び直しが失敗しても `exp - 30s` までは古い値で動く。

短寿命の token を毎回発行するなら、署名に使う鍵も短い周期で入れ替えたい。人が入れ替えると周期が守られず、`>` での上書きのような書き方の事故 (切り詰めた瞬間の空ファイルで署名が失敗する。同 findings の実測) も人の手順に残る。鍵束が設定の置き場 (`~/.config`、dotfiles で追跡) にあると、daemon が書いた秘密鍵が dotfiles の VCS に取り込まれる危険もある (2026-10-06 に取り込まれかけた)。

## 決定

### 1. 発行と入れ替えを分ける (kawaz 裁定)

発行は鍵を読むだけで、何も書かない。鍵のファイルを書くのは入れ替えだけ。

### 2. 発行コマンド `llm-gateway auth token` (kawaz 裁定)

```
llm-gateway auth token [--config <path>] --ns <ns> --sub <sub> [--kid <kid>] [--ttl <duration>]
```

- 設定から ns の `keys_file` と `max_ttl` を引いて署名し、stdout に token を 1 行だけ出す。失敗したら非 0 で終わり、stdout には何も出さない
- 署名に使う鍵は **最新の自動の鍵、無ければ `--kid` で指定した手の鍵**
- `--ttl` の既定は 1 時間。Claude Code の helper のキャッシュ (既定 5 分) はそのままでよい。`exp - 30s` で呼び直されるので期限切れの token は送られず、裏の呼び直しが失敗し続けても約 55 分は古い token で動く
- `max_ttl` を超える TTL は断る
- 名前を `refresh` にしない (OAuth の refresh token と紛れる)

### 3. 入れ替えは各 unit の daemon 自身が行う (kawaz 裁定)

手でも cron でもなく、gateway の daemon が入れ替える。起動時に確かめ、以後は鍵の作成時刻と寿命から次にやることの時刻を計算してタイマーを張る。定期的に見に行くポーリングのループは作らない。消す処理は細かく走らせず、cooltime でまとめる。

### 4. 書き手の調停はリーダーを決めずに flock (kawaz 裁定)

stable と unstable は同じ鍵のファイルを共有しうる。DR-0035 の thinking の出所 (`thinking_sources.rs`) と同じ形にする: `.lock` を flock で掴む → 読み直す → 「最新の自動の鍵がまだ若ければ何もしない」を確かめる → 書く → 手放す。どちらの unit が先に掴んでも、増える鍵は 1 本。

### 5. 自動の鍵と手の鍵を区別する (kawaz 裁定)

自動で作った鍵は JWK の行に印を付ける (`"auto": true` と作成時刻)。gateway が消すのは印のある鍵だけで、手で作った鍵 (`keys_file` の鍵) には一切触らない。手の鍵で作られた token の期限を gateway は知らないため。

印は 3 欄 (`"auto": true`、整数の `created`、正の整数の `max_token_ttl` (§11)) が揃って初めて印とする (worker の判断)。`auto` を名乗っていても欄が欠けた・型が違う行は、印の無い行と同じに扱う: 消さない (その鍵の token の寿命が分からないので、消すと有効な token を殺しうる)、`auth token` の署名にも使わない (上限を決められない)、検証には使う (手の鍵と同じ)。入れ替えのたびに、その kid を警告に挙げる。gateway が書く行は常に 3 欄揃いなので、欠けた行は人が書いたか壊れたかのどちらか。

### 6. 消す条件と書き方 (kawaz 裁定)

新しい自動の鍵ができてから「自動の鍵で発行できる token の寿命の上限 + 余裕」が過ぎた、古い自動の鍵だけを消す。新規は追記、削除は一時ファイル + `mv` (rename)。`>` で上書きしない。

### 7. 置き場は state 側 (kawaz 裁定)

自動の鍵は state 側の別ファイルに置き、検証は `keys_file` (手の鍵) と自動の鍵のファイルを両方見る。gateway が書き換える秘密鍵は、XDG の区分で設定でなく状態にあたる。設定の置き場に daemon が書くと、設定の書き手 (人と dotfiles) と daemon が混ざる。

### 8. 入れ替えの周期は設定で持てる (kawaz 裁定)

設定キーの名前・置き場所・既定値は §10。

### 9. kid は `<ns>-<日付>-<ランダム>` (kawaz 裁定)

例 `lab-2026-10-06-3fa9`。重ならず、events の `kid` を人が見て面と時期が分かる。日付は作成した unit の地方時。

### 10. 周期の設定は ns ごとの `key_rotation` (worker の判断)

```toml
[ns.lab]
auth = "jwt"
keys_file = "~/.config/llm-gateway/keys/lab.jwks.jsonl"
max_ttl = "400d"
key_rotation = "7d"   # 任意。既定 7d、1h 以上
```

- ns ごとに置く。鍵束も `max_ttl` も ns ごとで、周期は鍵束の性質だから。`auth = "jwt"` の欄の 1 つで、他の方式と組み合わせると断る (`keys_file` / `max_ttl` と同じ扱い)
- 書かなければ 7 日。自動の鍵とその鍵の token が使える期間は最長で「周期の 2 倍 + 1 時間」(§11・§13) で、7 日なら漏れた自動の鍵も 2 週間あまりで自然に効かなくなる。書き込みは週に追記 1 回と削除 1 回で済み、1 日だと書き込みが 7 倍になって得るものが少なく、30 日だと漏洩が 2 か月効く
- 下限は 1 時間。`auth token` の既定の TTL (1 時間) が上限 (§11) に収まり、cooltime (1 時間、§13) より短い周期で鍵が積もらない
- 新しい設定キーはこれ 1 つ。自動の入れ替えを止める口は持たない。`auth = "jwt"` の ns は全部入れ替わる

### 11. 自動の鍵で発行できる TTL の上限は、作成時の `min(key_rotation, max_ttl)` を鍵の行に刻む (worker の判断)

自動の鍵で長い TTL を許すと、その鍵を消した瞬間にまだ有効な token が死ぬ。§6 の消す時刻を決めるには、自動の鍵の token の寿命に上限が要る。

- 上限は `min(key_rotation, max_ttl)`。周期を上限にすると、ある鍵の token は「次の鍵ができてから 1 周期」で全部切れ、同時に生きている自動の鍵は普段 2 本 (消す直前の 1 時間だけ 3 本) に収まる。別の定数を持たない
- **作成した時点の上限を、その鍵の行に `max_token_ttl` (秒) として刻む**。`auth token` はその値 (と `max_ttl` の小さい方) で TTL を断り、入れ替えは前の鍵の行の値で消す時刻を決める。設定から毎回計算すると、鍵を共有する 2 つの unit の `key_rotation` が食い違った時 (片方だけ reload した等) に、長い上限で発行した token を短い上限の unit が先に消しうる。行に刻めば、上限は鍵と一緒に共有される
- 長い TTL の token が要るなら手の鍵で `auth sign` を使う (§14)
- 上限を守らせるのは `auth token` だけ。`auth sign --key <自動の鍵のファイル>` で長い TTL を鋳造すると、その token はその鍵が消えるまで (後継 + `max_token_ttl` + 1h) 効き、`exp` まで生きるとは限らない。自動の鍵は `auth token` で使う

鍵の行は `auth keygen` の出力に 3 つの欄を足した形:

```
{"kty":"OKP","crv":"Ed25519","kid":"lab-2026-10-06-3fa9","d":"…","x":"…","auto":true,"created":1791270000,"max_token_ttl":604800}
```

### 12. 置き場は `[stats] dir` の下 `jwt-keys/<ns>.jwks.jsonl` (worker の判断)

- 置き場は `<[stats] dir>/jwt-keys/<ns>.jwks.jsonl`、脇に `<ns>.jwks.jsonl.lock`。ディレクトリは 700、ファイルは 600。`[stats] dir` の既定は `$XDG_STATE_HOME/llm-gateway/stats`
- `[stats] dir` は keepalive の控え (DR-0027) と thinking の出所 (DR-0035 §6) が使う「兄弟の unit が共有する走行状態」の置き場で、鍵のファイルも同じ性質を持つ。`[store] dir` は預かった credential の置き場で、gateway 自身の秘密を混ぜない (DR-0030 §5 の区別)。新しい置き場のキーは足さない
- `auth token` (daemon の外で動く CLI) は同じ設定ファイルを読むので、daemon と同じ置き場を導出する。導出は 1 つの関数 (`Config::auto_keys_path`) にあり、daemon の入れ替え・検証・CLI の 3 者が使う
- ns の名前がファイル名になるので、`auth = "jwt"` の ns は名前を英数字と `.` `_` `-` に限り、`.` で始まる名前を断る (設定の読み込み時)
- ファイル名は ns の名前で引く。`[stats] dir` を共有する 2 つの設定が同じ名前の ns を持てば、自動の鍵も共有する (§既知の端)

### 13. タイマーの張り方と cooltime (worker の判断)

- 次にやることの時刻は壁時計 (Unix 秒) で計算する: 最新の自動の鍵の `created + key_rotation` (入れ替え) と、各古い鍵の「後継の `created` + その鍵の `max_token_ttl` + cooltime」(削除) の早い方
- cooltime は 1 時間。消す時刻に足す余裕で、検証の時計の揺れ (`SKEW_SECS` の 60 秒) と、後継ができた瞬間に古い鍵で署名した CLI の読み遅れを覆う
- 決定 3 の「消す処理は cooltime でまとめる」は、cooltime を「消す時刻に足す余裕」と「1 回に寝る上限」の 2 つとして効かせる形で満たす (worker の解釈)。消す時刻は鍵ごとに決まり、時刻が来た回に、その時点で消してよい鍵を全部 1 回の書き換えで消す。定常では 1 周期に 1 本作り 1 本消すので、まとめるのと同じになる。複数の鍵の消す時刻が 1 時間の内に並ぶのは、周期を変えた直後や長く止まった後だけ
- 寝る長さは「次の時刻までの残り」と cooltime の小さい方。macOS の単調時計 (tokio の timer の元) はシステムのスリープ中に止まるので、何日も先の時刻へ 1 回で寝ると、スリープした時間だけ入れ替えが遅れる。起きたら壁時計と比べ、まだなら**ファイルを読まずに**寝直す。ファイルを読み書きするのは時刻が来た ns だけ
- `daemon reload` は入れ替えの仕事を起こし、全 ns をその場で確かめ直す (`jwt` になった ns の鍵をすぐ作る)
- 読めない・壊れた鍵のファイルは、`<ns>.jwks.jsonl.broken.<UTC の日時 YYYYMMDDTHHMMSSZ>` へ rename で退避し (その名前が既にあれば `.1`、`.2` … を足す)、新しい自動の鍵 1 本だけの束を一時ファイル + rename で書く。flock の内側で行い、元の置き場と退避先を警告に 1 度出す (kawaz 裁定)。「読めない」は検証側の読み手と同じく、読み込みが失敗する (権限等) か、中身が鍵束として読めない (JSON でない、JWK として不正、kid の重なり等) こと。ファイルが無い・空なのは壊れていない (最初の 1 本を作る)。上に書き足すと他の鍵を消しうるし、書かずに残すと入れ替えも削除も止まり、最後に読めていた自動の鍵が検証側で効き続ける (「影響」の保証が外れる)。退避すると古い自動の鍵の token は断られるが、helper は 401 を受けて token を取り直すので 1 往復で済む。退避したファイルは daemon が消さない (人が原因を見てから消す。秘密鍵を含みうる)。`check` の「設定に無い ns の自動の鍵」の警告には挙げない。退避できなければ (rename の失敗) 何も書かず、警告を出して cooltime 後に試し直す
- 一時ファイルは書き手が flock の内側でしか作らないので、flock を掴んだ時点で残っているものは落ちた書き手の残骸として消す

### 14. `auth token` の細部 (worker の判断)

- 自動の鍵がまだ無い (新版の daemon を 1 度も起動していない・daemon が動いていない・ファイルが読めない) 時は `--kid` の手の鍵 (`keys_file` の中) で署名する。`--kid` も無ければ非 0 で断り、daemon を起動するか `--kid` を書くよう言う。自動の鍵がある間は `--kid` を使わない (自動の鍵が無い時の落ちどころ)
- 手の鍵に落ちた時の TTL の上限は `max_ttl` だけ (手の鍵の寿命は人が管理する)
- 自動の鍵が古い (daemon が止まっていて入れ替わっていない) 時もその鍵で署名する。daemon が起きれば入れ替わり、古い鍵の token も §6 の条件までは通る
- ns の設定に `iss` / `aud` があれば、token にその値を入れる (そのまま検証を通る token にする)。`--sub` は検証と同じ規則 (空でない、128 バイト以下、制御文字なし) で先に断る
- `--config` は他の命令と同じく省略でき、既定の設定ファイルを読む
- 設定は全体を読み込み時と同じ検査に通す。別の ns の鍵束が読めない等、設定として壊れていれば発行もしない

### 15. `auth keygen` / `jwks` / `sign` は手の鍵の道具として残す (worker の判断)

- `keygen` / `jwks` / `sign` はこれまでどおり設定を読まず、鍵束のファイルだけを扱う。手の鍵 (長寿命の token、helper を使えないクライアント) の道具
- `token` だけが設定を読む。help は「helper から呼ぶ短寿命の発行 = `token`」「手の鍵で鋳造 = `sign`」と書き分ける

### 16. 検証は 2 つの鍵束を見る (worker の判断)

- `JwtAuth` が手の鍵束 (`ring`、`keys_file`) と自動の鍵束 (`auto_ring`) を持つ。kid は手の鍵束から引き、無ければ自動の鍵束から引く。kid が両方にあれば手の鍵を使う (自動の kid は作る時に手の kid と重ならないよう選ぶ)
- 2 つは別々の `KeyRing` で、それぞれ mtime を見て読み直し、空や壊れたファイルは採らずに前の束を保つ (今の規則のまま)
- **mtime を記録する (= 同じ mtime の間は読み直さない) のは、読めて、かつ読む前後の stat の mtime が同じだった時だけ**。読めなかった時は mtime を記録せず、次の検証でまた読む。警告は「最後に警告した mtime」を別に持ち、同じ mtime の間は繰り返さない。理由: 失敗した mtime を記録すると、daemon の追記の途中を読んだ unit は、同じ mtime のまま書き上がった中身を取りこぼし、次の書き換え (最長で 1 周期) まで新しい自動の鍵を `unknown_kid` で断り続ける。前後の stat を比べるのは、読めたが読んでいる間に書き換わった (どちらの版か分からない) 場合も次の検証で読み直すため。代わりに、壊れたままのファイルは検証のたびに読み直す (小さなファイルなので負担は小さい)。手の鍵束にも同じ規則を当てる
- 自動の鍵束はファイルが無くてもよい (新版を起動する前・最初の鍵を作る前)。無い間は空の束で、警告も出さない。あったファイルが消えたら、前の束を保って 1 度だけ警告する
- 自動の鍵束が起動時に読めなくても、起動は止めない (空の束で始め、警告を残し、次の検証からまた読む)。手の鍵束は読めなければ起動を止める (今の規則のまま)。gateway が自分で書くファイルの不具合で、手の鍵だけで動く ns まで止めない
- 自動の鍵束を結びつけるのは設定を読み込む時 (`Config::load`)。daemon の起動・`daemon reload`・`check`・`auth token` は全部この経路を通る

## 採らなかった案

- **発行コマンドが鍵も作る (無ければ作る)**: 発行が書き手になり、helper の数だけ書き手が増える。§1 の分離が崩れる
- **リーダーの unit だけが入れ替える**: リーダーの選出と引き継ぎが要り、リーダーが落ちている間は入れ替わらない。flock の内側で「若ければ何もしない」を確かめれば、誰が掴んでも結果は 1 本 (§4)
- **自動の鍵も `keys_file` に書く**: daemon が設定の置き場に書くことになる (§7)。手の鍵と同じファイルにあると、消してよい鍵の区別を行の印だけに頼ることにもなる
- **自動の鍵の TTL の上限を設定から毎回計算する**: 鍵を共有する unit の設定が食い違った時に、発行した token より先に鍵を消しうる (§11)
- **定数の上限 (例 1 日)**: 周期と別の数を 1 つ持つことになる。周期を上限にすれば、同時に生きる鍵の本数が周期だけで決まる
- **入れ替えの時刻まで 1 回で寝る**: macOS のスリープ中は単調時計が止まり、寝ていた時間だけ入れ替えが遅れる (§13)
- **鍵のファイルを定期的に見に行く**: 次の時刻はファイルの中身から計算でき、兄弟の unit が先に入れ替えても、こちらの時刻が来た時に読み直せば足りる

## 影響

- `auth = "jwt"` の ns は全部、`[stats] dir` の下に自動の鍵のファイルを持つ。helper を使わない ns にも作られ、state の置き場が漏れればその ns の token を偽造できる (手の鍵束が漏れた時と同じ種類の危険。置き場は 700 / 600)
- 自動の鍵の token は最長で「後継ができてから `max_token_ttl` + 1 時間」で必ず効かなくなる。漏れた自動の鍵は最長「周期の 2 倍 + 1 時間」で効かなくなる (人が何もしなくても)。鍵のファイルが壊れても、入れ替えの仕事が次の時刻に退避して作り直す (§13) ので保たれる。保たれないのは退避の rename もできない時 (置き場のディレクトリに書けない等) だけで、その間は警告が cooltime ごとに出る
- `daemon reload` で `key_rotation` を変えると、次に作る鍵から新しい周期と上限になる。作った鍵の上限は変わらない

### 既知の端

- **版が混在する間**: 自動の鍵のファイルを読まない版 (0.67.0 以前、例えば stable の 0.66.0) は、自動の鍵で署名した token を `unknown_kid` で断る。helper を `auth token` に切り替えるのは、同じクライアントが届きうる全 unit (Caddy の fail over 先の stable を含む) が新しい版になってから。古い版は自動の鍵のファイルに触らないので、新旧が同じ `[stats] dir` を共有しても壊れない
- **`key_rotation` を書いた設定は古い版で読めない** (`deny_unknown_fields`)。stable と unstable が同じ設定を読むなら、両方が新しい版になるまで `key_rotation` を書かない (既定の 7 日なら書かずに済む)
- **同じ名前の ns の共有**: `[stats] dir` を共有する 2 つの設定が、別の `keys_file` を持つ同じ名前の ns を書くと、自動の鍵は共有され、互いの自動の鍵の token を通す。stable / unstable のように同じ面を 2 つの unit で出す前提の置き場で、別の面を同じ名前で書かない
- **追記の途中で電源が落ちる**: 書きかけの行が残ると、次に入れ替えの仕事がそのファイルを読む回 (起動時・cooltime 後の試し直し・`daemon reload`) に §13 の退避で作り直す。それまで `auth token` は `--kid` に落ち (`--kid` が無ければ断る)、検証は最後に読めた束を使い続ける。作り直した後は残っていた自動の鍵の token が断られ、helper は 401 を受けて取り直す。退避した `.broken.<日時>` は原因を見てから人が消す
- **時計が大きく戻る**: `created` が未来の鍵は「まだ若い」として扱い、入れ替えは時計が追いつくまで起きない
- **ns の名前の制限は新しい版だけが課す**: 古い版で通っていた `jwt` の ns の名前 (`/` や空白を含む、`.` で始まる等) は、新しい版では設定の読み込みで断られる
- **ns を消した・改名した後も自動の鍵は残る**: state の `jwt-keys/<ns>.jwks.jsonl` (秘密鍵) は daemon が消さない (同じ置き場を別の設定の unit が使っているかもしれない)。同じ名前の `jwt` の ns を書き直すとその鍵がまた効く。`check` が設定に無い ns の自動の鍵を警告に挙げるので、全 unit からその ns が消えたら人が消す
- **`[stats] dir` を省くと置き場は呼び出したプロセスの `XDG_STATE_HOME` で決まる**: daemon と helper (Claude Code から起動される `auth token`) で env が違うと、別の置き場を見る。`[stats] dir` を明示するか、helper と同じ env で `check` を通して置き場を確かめる
