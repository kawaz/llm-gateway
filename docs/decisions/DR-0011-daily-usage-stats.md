# DR-0011: 応答の usage を credential × モデル × 日で積み、writer 毎の日次ファイルに残す

- Status: Active
- Date: 2026-07-30

## Context

「どのアカウントでどのモデルをどれだけ使ったか」を日単位で振り返る手段が無かった。

ccusage は単一 Claude アカウント分しか集計できず、複数アカウントを並べているこの
構成では合算できない。加えて叩くたびに全量を再集計するので遅い。**一度過ぎた日の
集計は確定している**ので、確定分を残して当日分だけ足していけば足りる。

gateway は全アカウントの中継点なので、応答が通る場所で数えるのが一番素直。しかも
upstream は消費したトークン数を**応答に載せて返してくる**ので、追加の API コールは
要らない。

既存の `/llm-gateway/usage` (DR-0007) は**応答ヘッダ**から「上限にどれだけ近いか」を
読む仕組みで、今この瞬間のスナップショットしか持たない。知りたいのは
「いつ・どれだけ使ったか」の蓄積で、軸が違う。

## Decision

### 蓄積は usage.rs (ヘッダ由来) と統合せず、別に置く

軸が直交している。

| | `usage` (DR-0007) | `stats` (本 DR) |
|---|---|---|
| 読む場所 | 応答**ヘッダ** | 応答**本文** |
| 表すもの | 上限への近さ (使用率・リセット時刻) | 消費したトークン量 |
| 時間 | 今この瞬間のスナップショット | 日ごとの蓄積 |
| 永続化 | する (最後の観測を持ち越す、DR-0007) | する (作り直せない) |
| 失った時 | 次のリクエストで拾い直せる | 二度と戻らない |
| 単位 | credential | 日 × credential × モデル |

どちらもディスクに落とすが、落とす理由が違う。`usage` は再起動直後に一覧が空に
ならないための控えで、失っても次のリクエストで埋まる。`stats` は失うと二度と
戻らない。1 つの構造体に混ぜると、保存する形も鮮度の意味も分岐する。

### 本文を覗く層は relay の外に置く

`relay.rs` は「本文は解釈せずクライアントへ素通しする」を柱にしている。SSE の
バイト列がそのまま通り抜けることが中継の正しさなので、ここに usage の解釈を
足さない。

代わりに `BodyStream → BodyStream` の変換層 (`stats::tap`) を別に作り、受け取り口
(`llm-gateway-server` の `messages`) で `relay::observe(stats::tap(body, ...), span)`
の形に挟む。**`relay.rs` は無変更**。

tap は通り過ぎるチャンクを下流へそのまま渡し、控えの側だけを進める。試験で
「1 バイトも変えない」ことを確かめている (実機でも SSE が原文どおり流れることを
確認済み)。

集計できない応答には層を重ねない:

- **2xx 以外**: エラーの本文に usage は載らない
- **content-type が `text/event-stream` / `application/json` 以外**: 読み方が
  決まらない。中身を推測して読みに行くと、画像やバイナリを JSON として抱え込む

### usage の値は累積。足さずに置き換える

#### 観測事実 (2026-07-30)

この節は**実機で観測した事実の記録**であって、公式ドキュメントの引用ではない。
upstream が semantics を変えたときに、ここと突き合わせて「変わった」と言えるように
残す。SSE の usage は公式に明文化されていないので、疑わしくなったら再観測する。

- 観測日: 2026-07-30
- 条件: `claude-haiku-4-5-20251001` / `max_tokens` 16 / `"stream": true` /
  入力 18 token / `stop_reason: max_tokens`
- 経路: gateway (`/ns-<名前>/v1/messages`) 経由で生 SSE を `curl -N` で受けた

| イベント | 位置 | input | cache_creation | cache_read | output |
|---|---|---|---|---|---|
| `message_start` | `/message/usage` | 18 | 0 | 0 | 1 |
| `message_delta` | `/usage` | 18 | 0 | 0 | **16** |

読み取れた 2 つ:

1. `message_delta` の `output_tokens` は**差分ではなくその時点の総量**。足すと
   `1 + 16 = 17` になって実際より多く数える
2. `message_delta` は input と cache も**再掲**する (= 出力専用のイベントではない)

再観測の手順は上の条件そのまま。`max_tokens` を小さく取るのは、`output_tokens` が
その値で止まるので「累積か差分か」が一目で分かるため (差分なら最後の delta は
16 より小さい値になる)。

`cache_creation` / `cache_read` は**この観測では 0 しか出ていない** (フィールドの
存在と読み取りは確認済み、非ゼロ値は未観測)。プロンプトキャッシュを使う応答が
通れば埋まるはずだが、そこは未確認。

したがって「usage オブジェクトを見つけたら、**載っているフィールドだけを後から来た
値で上書き**」で扱う。イベント名で拾う先を決め打ちせず、`data:` 行の JSON の
`/message/usage` と `/usage` の両方を見て在る方を吸収する。この形なら、
`message_delta` が複数回来ても、一部のフィールドしか載せなくても崩れない。

#### 読む単位は行ではなくイベント

SSE では**同じイベントの連続する `data:` 行を改行で繋いだものが 1 つの中身**。
行ごとに JSON として解こうとすると、準拠した upstream が usage を複数行に割った
ときに黙って取りこぼす (今の upstream は 1 行で返してくるが、そこに寄りかかる
理由がない)。

そこで空行 (イベントの終わり) まで `data:` を溜めてから解く。`event:` / `id:` /
注釈行は読まない。解くのは `"usage"` を含むイベントだけ — イベントは 1 応答で
何十個も流れるので、全部解くと中継の脇で無駄に働く。

終端が空行で閉じられていなければ、最後のイベントは本文の終わりで閉じたものとして
扱う (中断された応答でも、そこまでに届いた分を読む)。

### 記録は tap の Drop で 1 回だけ

正常に流し切った場合と、クライアントが去って途中で捨てられた場合を**同じ道**に
まとめる。Drop は 1 度しか走らないので、二重に数える形にならない (終端で記録して
Drop でも記録する作りだと、両方通る経路で倍になる)。

**途中まで流れた応答も、そこまでに読めた分を記録する**。`message_start` まで
届いていれば入力の消費は確定しているので、中断を理由に丸ごと捨てると実際に使った
分が記録から消える。

usage が 1 つも載っていなかった応答 (`count_tokens` 等) は**記録しない**。本数だけ
増えると、使っていない日が「使った日」に見える。

### 抱え込む量に上限を置く

- SSE の 1 行: 256 KiB。行の途中でチャンクが切れるので行が揃うまで持つ必要が
  あるが、改行を返さない相手にメモリを食い潰されない (実際の `message_start` は
  1 KB 前後なので桁が違う)
- ストリームでない本文: 4 MiB

超えたら**その応答の集計だけ諦めて、素通しに徹する**。集計を捨てることと中継を
止めることは別 — 本文は最後まで流し続ける。

### 保存は writer 毎の日次ファイル。排他を構造で消す

置き場は `$XDG_STATE_HOME/llm-gateway/stats/` (`[stats] dir` で変えられる)。
ファイル名は **`YYYY-MM-DD.<待ち受け先>.json`**、中身は `credential → モデル →
集計`。

同じ置き場を複数の gateway (8401 / 8402) が共有するが、**書き込み先がプロセスごとに
分かれている**ので排他が要らない。読む側が全ファイルを足し合わせる。DR-0010 の
flock 基盤は流用しない — 排他が必要な状態そのものを作らない方が単純。

- **1 リクエストごとには書かない** (kawaz 裁定: 無駄)。60 秒間隔 + 終了時
- **変わった日だけ書く**。目印は日ごとに持つ。全体で 1 つにすると、1 件積むだけで
  メモリに載っている全部の日を書き直すことになり、「過去日のファイルは読むだけ」と
  食い違う
- **書き手は 1 人に絞る** (`writing` の Mutex)。定期の保存と終了時の保存は重なりうる。
  重なると同じ一時ファイルを 2 者が切り詰め合い、混ざった中身が rename される /
  片方が消したファイルをもう片方が rename しようとして失敗する。終了時は定期の側を
  止めて待ってから最後の保存に入り、名前にも通し番号を混ぜて二重に塞ぐ
- 書き込みは一時ファイル (`+pid+連番`) → `sync_all` → rename。読む側が途中の状態を
  読まない (DR-0010 と同じ理由で名前に pid を混ぜる)。rename まで進めなかった残骸は
  **起動時に自分の分だけ掃除**する (他の writer の一時ファイルは書いている途中かも
  しれないので触らない)
- **起動時に自分のファイルを読み戻す**。読まずに 0 から数え直すと、次の保存で
  前回までの分を**上書きして消す**。載せるのは**当日と前日だけ** — 書き足す予定の
  ある日はそこまでで (深夜に始まった応答が明けてから終わると前日にも積む)、それ以前は
  閲覧時にファイルから読めるので常駐させる必要がない
- メモリに無い日へ積むときは、**その日のファイルを先に読んで土台にする**。読み戻しの
  範囲外へ積む形 (時計が巻き戻った等) でも上書きで消さない
- 日を跨いだら新しい日付の欄に積むだけ。保存側が日付ごとのファイルに振り分けるので、
  跨いだ直後に残っている前日分も正しい先へ行く
- 過去日のファイルは**読むだけ**。再集計・書き換えをしない (例外は読み戻し範囲外の日へ
  record が落ちた場合だけ — その日はファイルを土台に読んでから加算・保存するので消えない)

閲覧時、**メモリに載っている日だけ**自分のファイルを読み飛ばす。その日は落とした分が
ディスクとメモリの両方に居るので、素直に足すと倍になる。載っていない過去日は
メモリに無いのでファイルから読む (読み戻しを直近に絞っても過去日が消えない)。

### 見え方の限界: 他の writer の未保存分は遅れて現れる

閲覧は「全 writer のファイル + 自分のメモリ」を合わせたもの。**他の writer が
まだ落としていない分は見えない**ので、最大で相手の保存間隔 (60 秒) だけ遅れて
現れる。自分の分は落とす前でも出る。

これを消すには writer 間で今の値を問い合わせる仕組みが要るが、日次の振り返りに
60 秒の遅れは効かないので採らない。

### 日付は地方時で決める

UTC で数えると JST では日の境目が朝 9 時になり、「今日どれだけ使ったか」が体感と
ずれる (置き換え対象の ccusage も地方時)。

このリポには日時ライブラリが無く (`credential/time.rs` が civil 変換を手書き)、
std には地方時の口が無い。**`libc` を直接依存に足して `localtime_r` を借りる**。
offset は夏時間の有無と切り替え時刻で年内にも動くので、`TZ` と OS のタイムゾーン表を
読む相手に任せるしかない。libc は既に依存グラフに居る (rustix / tokio 経由)。

unsafe はこの 1 関数 (`local_offset`) に隔離する。条件は 3 つ:

- **`// SAFETY:` で不変条件を明記する**。ゼロ埋め初期化が成り立つ理由 (`libc::tm` は
  repr(C) の整数と生ポインタだけででき、全 0 がどのフィールドでも有効な値)、
  `localtime_r` が**スレッドセーフ**である理由 (`localtime` の共有 static と違い、
  渡した `tm` にだけ書く再入可能版)、そして残る前提 (**`TZ` を書き換える者がいない
  こと** — 書き換えと同時に読むとデータ競合。この crate は `std::env::set_var` を
  呼ばず、edition 2024 ではそれ自体が unsafe)
- **日付の計算は offset を引数で受ける純関数** (`date_at_offset(unix, offset)`) に
  分ける。実機のタイムゾーンに依らず、offset の**正負**と**日の境目**を試験できる
  (東 +14h / 西 -7h、地方時 00:00:00 の前後 1 秒、epoch より前)
- `tm_gmtoff` は POSIX ではなく BSD / glibc の拡張。対象が macOS (DR-0010) と
  Linux なのでどちらにもある

実機確認 (2026-07-30): unix 1785355200 は UTC では 2026-07-29 だが地方時では
2026-07-30 で、`local_date` は後者を返す (`date -d @1785355200 +%F` と一致)。
`local_offset` は 32400 (= +09:00) で `date +%z` と一致。

### 閲覧は `/llm-gateway/stats` と `llm-gateway stats`

エンドポイントは healthz / usage と同じ扱いで認証を掛けない。出すのはトークン数
だけで、何を書いたかは残していない。`?days=N` で直近 N 日 (既定 7、0 で全期間) —
全期間を返すと日が経つほど応答が伸びる。読めない `days` は 400 で断る (黙って
既定に落とすと、絞ったつもりの相手が別の範囲を見る)。

CLI は集計を持たず HTTP で聞いて整形するだけ (usage と同じ形)。日ごとに合計を先に
出し、内訳を字下げして 1 つの桁組に並べる。桁は全日で揃える (日ごとに幅が変わると
縦に並べて比べられない)。

### 転送の結果に身元を添える (`Forwarded`)

集計の鍵には「どの credential が答えたか」と「解決後のモデル名」が要る。
`Gateway::forward` の戻り値を `Forwarded { response, credential, model }` にした。

`forward::Response` に足さない。あれは HTTP の応答そのもの (状態・ヘッダ・本文) を
表す型で、集計の都合を混ぜると転送に関係のない項目が溜まっていく。

モデル名は**解決後**のもの。短い名前 (`opus`) のまま集計すると、同じモデルが別名の
数だけ行に分かれる。認証情報を持たない経路 (relay 型) は `None` で、集計では予約名
`-` に振る (落とすと合計が合わなくなる)。

断られた応答 (429 等、DR-0009 の透過) にも身元は付くが、これは**どの経路を通って
返る応答でも同じ形 (応答 + 身元) にするため**で、集計に乗るという意味ではない。
**集計対象は 2xx だけ**。429 の本文に usage は無く、ここで数えたいのはトークン量
なので、断られた回数は別の関心事 (数えたくなったら `usage` 側か新しい軸で扱う)。

## やらないこと

- **リクエスト毎のディスク書き込み** (kawaz 裁定: 無駄)
- **既存 usage.rs への統合** — 軸が直交、上表のとおり保存の要否から違う
- **過去日の再集計・書き換え** — 確定した日を触る理由が無い
- **コスト ($) 換算** — 集計はトークン量のみ。単価はモデルと契約で変わり、
  過去日の記録に当時の単価を貼り付ける話になる。必要になったら表示側で足す
- **複数 writer が同一ファイルを書く設計** — writer 毎ファイル + 読み時マージで
  排他自体を消す

## Alternatives Considered

**relay.rs の中に tap を組み込む** — 包む層が 1 つ減るのは利点だが、「本文は解釈
しない」という中継の柱を崩す。あの素通しは SSE が upstream 間で同形だから成立して
いるもので、解釈を足すと形が変わったときに中継そのものが壊れる。覗くのを外に出せば、
壊れても集計が止まるだけで中継は流れ続ける (実際、上限超過で諦める経路がそうなって
いる)。

**`forward::Response` に credential / model を足す** — 呼び出し側の変更が 1 行で
済むが、HTTP の応答を表す型に集計の都合が入る。次に「namespace も欲しい」
「経路名も欲しい」となったとき、足す先がここになってしまう。

**単一の共有ファイル + flock** — DR-0010 の基盤が既にあるので流用できるが、
待ちと失敗の経路が増える。writer を分ければ排他が要る状態が生まれない。読む側の
マージは足し算なので、複雑さの総量はこちらが小さい。

**`jiff` / `chrono` を足して地方時を出す** — unsafe を書かずに済み、tzdb の扱いも
正しい。採らないのは、この 1 用途 (日付の文字列) に対して依存が重いこと。
`credential/time.rs` が既に RFC 3339 と civil 変換を手書きしている方針とも揃う。
`time` crate の `local-offset` は多スレッドで offset の取得を拒む作りなので、
tokio 上のこの用途には合わない。

**UTC で日を数える** — 実装が最も単純だが、JST では日の境目が朝 9 時になる。
午前中の作業が前日に計上されるので、「今日いくら使ったか」に使えない。

**message_start と message_delta で拾うフィールドを分ける** (`message_start` から
input/cache、`message_delta` から output) — 実測で `message_delta` が input と cache
も再掲すると分かったので、役割で分けるより「載っているものを上書き」が単純かつ
頑健。イベント名が増えても追従が要らない。
