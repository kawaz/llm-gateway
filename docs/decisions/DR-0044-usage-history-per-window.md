# DR-0044: 枠の利用率の推移を、枠が 1 段動くたびに 1 行、その間に流したトークンをモデル別に添えて追記で貯める

- Status: Accepted (記録の単位と添える量は kawaz 指示 2026-11-17。置き場・起点・切り替わりの扱いは実装側の判断で、残りは「未確定」)、実装済み (未リリース)
- Date: 2026-11-17

## Context

「あるモデルは別のモデルより、定額プランの枠を API 換算額あたり数倍速く減らす (cache read の計上が非対称)」という外部の主張を、手元の実データで確かめたい。確かめるには「ある区間に枠の利用率がどれだけ動いたか」と「同じ区間にどのモデルで何トークン流したか」が対で要る。

今ある記録はどちらも片方しか持たない:

| 記録 | 持っているもの | 足りないもの |
|---|---|---|
| 日次集計 (DR-0011) | 日 × credential × モデル × 区分のトークン量 | 日より細かい時刻。枠の利用率 |
| usage スナップショット (DR-0007) | credential ごとの最新の利用率 | 推移 (上書きされる) |

ログにも利用率は出ていない。

### どの枠が、いつ取れるか (2026-11-17 に実装を読んで確認)

| 経路 | 枠 | 取れる契機 |
|---|---|---|
| 応答ヘッダ | `5h` / `7d` の窓 (Anthropic は `utilization` 0.0〜1.0 を 1 % 刻み、Codex は primary / secondary を同じ欄に載せ、周期は `window_seconds`) | 転送の応答のたび。`usage?refresh=true` の最小リクエストも |
| 枠照会 API (`QuotaApi`) | upstream が返す全部。Anthropic は `session` / `weekly_all` / モデル別の `weekly_scoped` (`percent` 0〜100)、Codex は primary / secondary | 聞きに行った時だけ。`usage?refresh=true`、`pace_cap` の経路で枠が読めていない時 (DR-0019 §6)、締め出し中の経路の裏の照会 (DR-0009) |

モデル別の枠は応答ヘッダに出ない (DR-0009)。応答ヘッダと枠照会 API は同じ「7 日」でも値が一致しない別の物差し (DR-0007)。

## Decision

### 1. 1 行 = 1 つの枠の 1 回の動き

枠ごとに、利用率が動いた時だけ 1 行を書く。行の種類は `change` が言う:

| `change` | いつ | 添えるもの |
|---|---|---|
| `start` | このプロセスがその枠を初めて見た | なし (差を数える起点) |
| `step` | 利用率が上がった | `from` (前の行の値)、`since` (前の行の時刻)、`tokens` (その間に流した量) |
| `rollover` | 窓が切り替わった、または利用率が下がった | なし (起点を置き直す) |

値が変わらない観測は行にしない。応答のたびに来るので、書くと応答の数だけ行が並び、その間の量は次に動いた行へまとめて入るので失わない。Anthropic の `utilization` は 1 % 刻みで来るので、`step` 1 行が 1 % の 1 段に当たる。大きな 1 本で 2 段以上一度に動いた時も 1 行で、段の数は `from` と値の差で読む。

1 行の例 (credential 名は架空):

```json
{"observed_at":1785326460000,"credential":"claude-a","change":"step","source":"headers","window":"7d","utilization":0.31,"status":"allowed","reset":1785888000000,"window_seconds":604800,"from":0.30,"since":1785326400000,"tokens":{"claude-opus-5":{"requests":4,"tokens":{"input":120,"input.cache_read":480000,"input.cache_creation.ephemeral_5m":9000,"output":3100}}}}
```

```json
{"observed_at":1785326500000,"credential":"claude-a","change":"start","source":"quota_api","kind":"weekly_scoped","percent":20.0,"severity":"normal","resets_at":1785888000000,"model":"Fable","window_seconds":604800,"is_active":false}
```

- 時刻は Unix ミリ秒の数 (DR-0007 / DR-0012 と同じ規約)
- 枠の欄は経路の語のまま持つ。応答ヘッダの窓は usage スナップショットの窓 (`Window`) と同じ欄 (`utilization` / `status` / `reset` / `window_seconds`) に、欄名 `window` (`5h` / `7d`) を添える。枠照会 API の枠は usage の `limits[]` の 1 件 (`QuotaLimit`) と同じ欄。言い換えて 1 つの物差しに揃えないのは、両者が同時刻に違う値を返す別の物差しだから (DR-0007)。`from` は値と同じ物差し
- `tokens` は日次集計のファイルと同じ形 (モデル → `{requests, tokens: {区分: 数}}`)。区分も同じ名前で、upstream が言った数のまま (OpenAI の `input` は cache 分を含む。揃えるのは読む側で、日次集計の閲覧と同じ単価表の内訳の宣言を使う、DR-0011)

### 2. 系列は (credential, 経路, 枠, モデル) で分ける

5 時間の窓と 7 日の窓は別々に数える。7 日の 1 段は 5 時間の何段分にも当たるので、起点を共有すると 7 日の行に添える量が「前に 5 時間の窓が動いてから」に縮む。枠照会 API の枠は種類 (`kind`) とモデル (`model` / `model_id`) ごと。同じ周期でも応答ヘッダの窓と枠照会 API の枠は別の系列にする。

### 3. 窓の切り替わりは「前のリセット時刻を過ぎたか」で判定する

前に見たリセット時刻を過ぎた観測で、リセット時刻が変わっていたら `rollover`。利用率が下がった観測も `rollover`。

- リセット時刻が変わっただけでは切り替わりと見ない。切り替わっていない窓のリセット時刻が観測ごとに揺れると、そのたびに起点が置き直されて差が数えられなくなる (Codex の `reset-at` が窓の中で一定かは未確認。この判定ならどちらでも壊れない)。揺れた後の時刻は覚えておき、次の判定に使う
- 過ぎたリセット時刻をそのまま言い続ける観測は切り替わりと見ない (毎回切り替わりにすると応答のたびに行が並ぶ)
- 切り替わりをまたぐ区間には前の窓の分 (最後の値は見えていない) と新しい窓の分が混ざるので、1 段あたりの量として読めない。だから差を添えずに起点を置き直す

### 4. トークンはこのプロセスが起動してから積んだ累計の差

日次集計の器 (`Stats`) が、日次のファイルとは別に「起動してからの累計」(credential → モデル → 集計、素性は合算、ディスクには落とさない) を持つ。行を書くたびにその時点の累計を覚え、次の `step` で差を取る。

- 素性 (main / sub / keepalive …) を分けない。gateway の自送信も手元の 1 本と同じ枠を減らす
- 日次のファイルから引かない。日の境目と、読み戻した前回までの分が差に混ざる
- 数える場所は日次集計と同じ (応答本文の usage を読み終えた時点)。`usage?refresh=true` の最小リクエストは日次集計に積まれないので `tokens` にも入らない

### 5. 起点はプロセスごとに置く

起動したプロセスは、各系列を最初に見た値の `start` から数える。系列の状態はディスクに残さず、読み戻さない。前のプロセスが最後に書いた値を起点にすると、停止中の利用率の動き (このプロセスが流していない分) が起動後のトークンに付く。再起動の前後で区間は途切れる。

枠照会 API でしか取れない枠は、その枠を初めて聞けた時が起点になる。

### 6. 置き場は書き手ごとの日次ファイル、追記のみ、消さない

- パス: `<[stats] dir>/usage-history/<YYYY-MM-DD>.<書き手>.jsonl`。日付は観測時刻の地方時、書き手の名前は待ち受け先 (日次集計と同じ、DR-0011)。日次集計と同じ階層に並べず下に分けるのは、日次集計が置き場を走査して日付で始まる `.json` を読むので、同じ階層では名前の形だけで取り違えを防ぐことになるため
- 1 行 1 件の JSON を追記する。一度書いた行は書き換えない
- 書くのは日次集計と同じ 60 秒の保存の周回と終了時 (DR-0011 の「1 リクエストごとには書かない」)。落とすまではメモリに溜める。異常終了すると最後の周回から後の行を失う
- 書き込みは **best-effort**。書けなかった行は溜め直して次の周回で書き、転送は止めない (保存の周回が警告を残す)
- 前回の書き込みが行の途中で途切れていたら、次に足す前に改行で閉じる。途切れた行そのものは読み手が読み飛ばす
- 古い日のファイルは消さない。日次集計と同じく作り直せない記録で、量は小さい。見積もり: `step` 1 行が 300〜500 バイト、Anthropic の 5 時間の窓を 1 日に 5 回使い切る credential でも 1 日 500 段ほどなので、1 credential × 1 書き手で 1 日最大 250 KB。5 credential を stable / unstable の 2 書き手で使う最悪で 1 日 2.5 MB (年 1 GB 弱)、普段はその数分の 1。読み手は欠けた日を「行が無い」と読めばよいので、手で消しても壊れない

### 7. DR-0031 では (3) の仲間に置き、新しい trait は切らない

書き手ごとに自分の分だけを書き、読む側が全書き手の分を合わせる。合わせ方は**行の和集合** (時刻で並べる)。和集合は可換・結合的で空集合が単位元なので、DR-0031 §2 (3) の merge 則を満たす。`write_own` (自分の累計で上書き) は、自分の行が書き換わらないので「新しい行を足す」と同じになり、追記で実装する。`write_own` / `read_merged` はどちらも best-effort (stats の閲覧と同じ倒し方)。

(4) の LWW スナップショットではない。新しい観測が古い観測を置き換えず、全部を残すのが目的。

trait としては切らない。file 以外の backend が無い今、DR-0031 §5 と同じく使う時点まで遅らせる。file の器は汎用層に `gateway_core::daily_log::DailyLog` (日の振り分け・ファイルの置き方・追記の作法だけを持ち、1 行の形は利用側が決める) として置き、行の形と行を足す判断は `llm-gateway` の `quota::history` が持つ。

### 8. 読み方 (読む道具は作らない)

今回の範囲は貯めるところまで。読む側の手順をここに固定しておく:

- **1 つのプロセスだけが流していた期間**: `step` の行をそのまま読む。1 段 (`値 - from`) あたりの `tokens`
- **複数のプロセス (stable / unstable) が同じ credential で流していた期間**: 行単位では読めない (各プロセスの区間の境目が揃わず、同じ 1 段を両方が `step` として書くこともある)。期間 [t0, t1] で合わせる — 利用率の増分は全書き手の行を時刻で並べた値の差で取り (段の数を行の数で数えない)、トークンは全書き手の `step` の `tokens` の和。境目で各書き手 1 段ぶんの誤差が残るが、数時間〜日の期間なら効かない
- `rollover` をまたぐ期間は窓ごとに分けて足す

## 記録の限界

- **gateway を通らない利用は数えられない**。同じ credential を別のマシン・Web・gateway を通さないクライアントから使った分は利用率を動かすが、`tokens` には現れない。その区間の 1 段あたりの量は実際より少なく見える
- **応答 1 本ぶんのずれ**。利用率は応答ヘッダが届いた時点、トークンは本文を読み終えた時点で数えるので、1 本の応答のトークンはその 1 本のヘッダで動いた段ではなく次の段に入る (upstream がヘッダの利用率にその 1 本を含めているかは確かめていない)。区間の境目が 1 本ぶん後ろへずれる。ずれ方は一定なので並べて読めば打ち消し合うが、並行して流している時はどの 1 本がどの段に効いたかの対応がもっと緩む
- **モデル別の枠はまばら**。枠照会 API は Context の契機でしか聞かないので、普段使いではモデル別の枠の行は少ない (未確定)

## Alternatives Considered

- 案 A: スナップショット全体を値が変わった時に 1 行 (トークンを添えない)
  - 不採用理由: 1 段あたりの量を読むには、日次集計 (日単位) と時刻で突き合わせる必要があり、段の境目に揃えられない。kawaz 指示 (2026-11-17) で「1 % 動くたびに 1 行、その間に流した量をモデル別に添える」に決めた
- 案 B: 兄弟のプロセスで今の区間の累計を共有する (flock で調停する共有ファイル)
  - 不採用理由: 排他が要る状態を作ると、待ちと失敗の経路が転送の脇に増える (DR-0011 と同じ判断)。複数プロセスの期間は読む側で期間単位に合わせれば足り (決定 8)、共有しても gateway の外の利用は数えられないので、得られる精度は限られる
- 案 C: 系列の状態をディスクに残し、再起動を跨いで区間を続ける
  - 不採用理由: 停止中に動いた利用率を、起動後のトークンに付けてしまう (決定 5)
- 案 D: リセット時刻が変わったら切り替わりとみなす
  - 不採用理由: 窓の中でリセット時刻が揺れる upstream では、揺れるたびに起点が置き直されて差が数えられない (決定 3)
- 案 E: 1 応答ごとに即座に追記する
  - 不採用理由: 1 リクエストごとには書かない (DR-0011 の kawaz 裁定)。失うのは異常終了時の最後の 60 秒ぶんだけ
