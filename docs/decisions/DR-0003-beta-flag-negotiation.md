# DR-0003: upstream が拒否する beta フラグを credential 単位で学習する

## Context

Claude Code は `anthropic-beta` ヘッダに複数のフラグを載せて送る。実測
(Claude Code 2.1.220 の実リクエストを 8319 のプローブで観測) では 8 個で、
そのまま Bedrock へ透過すると 400 になる。**8 個中 4 個**
(`oauth-2025-04-20` / `prompt-caching-scope-2026-01-05` /
`advisor-tool-2026-03-01` / `extended-cache-ttl-2025-04-11`) が拒否され、
beta 無しなら 200 が返る。

拒否される顔ぶれは固定ではない。

- **クライアントのバージョンで変わる**。llm-notes findings が測った束 (cpa の
  注入値) とは中身が違い、`thinking-token-count` / `advisor-tool` /
  `extended-cache-ttl` は findings に無かった
- **upstream の対応でも変わる**。今日拒否されるフラグが明日は受理される
- **region で変わりうる**。Bedrock は region ごとに使えるモデルが違うので、
  受け付ける beta も揃っている保証がない

固定リストを設定に持つと、どの軸の変化でも人手の追従が要る。

## Decision

**credential ごとに「拒否されたフラグと最終確認時刻」を持ち、24 時間経ったら
再試行する。**

```json
{
  "type": "claude_bedrock",
  "denied-beta": {
    "advisor-tool-2026-03-01": "2026-07-28T09:28:21+09:00"
  },
  "payload": { ... }
}
```

判定:

| 状態 | 動作 |
|---|---|
| `denied-beta` にあり、最終確認から 24 時間未満 | 落とす (最近試した) |
| `denied-beta` にあり、24 時間以上経過 | **通してみる**。400 なら時刻を更新 |
| `denied-beta` に無い | 通す。400 なら追加 |

400 を受けたら該当フラグを外して 1 回だけ再試行する。

### なぜ credential 単位か

upstream が違えば可否も違う。`bedrock-us-east-1` と `bedrock-ap-northeast-1` は
別の upstream なので、片方の観測を他方に流用してはいけない。credential は
「どこに、どの資格で繋ぐか」の単位なので、観測結果の帰属先として正しい。

### なぜ最終確認時刻を持つか

拒否リストを恒久化しないため。upstream が対応すれば自動で復帰する。
時刻が無いと「一度拒否されたら永久に落とす」になり、新機能を取りこぼし続ける。

間隔は 24 時間の経過で判定する。日付境界にすると TZ をどう扱うかが問題になるが、
経過時間なら比較が一意に決まる。

### なぜ許可リストを持たないか

「通る」は `denied-beta` に無いことで表現できる。別リストを足しても判定に
寄与せず、2 つの真実を同期させる手間だけが増える。

### なぜ TZ 付き ISO 8601 か

同じファイル内の `expired` / `last_refresh` が RFC 3339 なので揃える。
epoch ms だと時刻表現が 2 種類混在して読み手が迷う。TZ を明示するのは、
人が読んだときにも書いた時点が一意に決まるようにするため。

### なぜ payload でなくトップに置くか

`denied-beta` は gateway が観測した運用知識であって、プロバイダが返した
認証情報ではない。`last_refresh` と同じ層に属する。

### 全 credential 種別に持たせる

`claude_oauth` は現状フラグを落とす必要がないが、同じ仕組みを持たせる。
公式 API も将来 beta を絞りうるし、種別で実装を分岐させる理由がない。
空なら何も起きない。

## Alternatives Considered

**許可リストを設定に持ち、列挙されたものだけ通す** (cpa の現行方式) —
未知フラグを黙って落とすので、新機能が出るたびに気づかないまま欠ける。
cpa は「束ごと置換」した結果 `context-management` を落として実障害を出した
(llm-notes DR-0001)。**落とす方向のミスは 400 が返らないので検出できない**のが
致命的で、通す方向のミスは必ず顕在化する。安全側は楽観側にある。

**Bedrock 向けは `anthropic-beta` を丸ごと落とす** — 受理される 4 機能を捨てる。

**拒否リストのみ (時刻なし)** — upstream が対応しても復帰しない。

**学習結果をプロセス内メモリだけに持つ** — 再起動でリセットされ、日付判定も
できない。設定ファイル (`config.toml`) への書き戻しは、人が編集するファイルを
機械が書き換えることになるので採らない (cpa の書き戻し問題と同じ道)。
credential ファイルは元々 gateway が書く場所なので、そこに置く。

## Consequences

- 未知フラグに対して 1 回だけ 400 のレイテンシが乗る。24 時間以内の 2 回目以降は無い
- upstream の対応は最大 24 時間遅れで反映される
- credential ファイルの書き込み頻度が上がる。複数プロセスが同じ store を共有する
  構成では競合しうる (OAuth refresh token と同じ問題)
