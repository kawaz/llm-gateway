# DR-0029: 日次集計に「出した側」(origin) の軸を足す

- Status: Active
- Date: 2026-09-14

## Context

DR-0027 で keepalive は合図の注入をやめ、gateway が最後に転送した本文を自送信
(replay) する形になった。自送信は request event に `origin: keepalive` で出て、
usage も stats に**普通の 1 本として**計上される (DR-0027 決定 6)。

ところが DR-0011 の日次集計は **credential × モデル × 日** の 3 軸しか持たない。
このため「ping が何本出て、いくら掛かったか」を集計から取り出せない。
`docs/findings/2026-09-08-keepalive-field-observation.md` の実運用評価では、
セッション jsonl を走査して ping 分を手で引くという**今回限りの遡及手段**で
代替している。gateway の外の成果物 (セッションログの形式と置き場) に依存する
数え方で、正本にできない。

素性そのものは既にある。`provider::RequestOrigin` (DR-0012) が
`main` / `sub` / `oneshot` / `codex` / `unknown` / `keepalive` の 1 語を答え、
転送のたびに知らせ (`/llm-gateway/events`) へ載っている。**知らせは流れて消える**
ので、日をまたいで振り返る口 (stats) には残らない。

## Decision

### 素性は集計の鍵に足す。モデルの下、いちばん内側に置く

保存する形を `日 → credential → モデル → **素性** → 集計` にする。

素性を鍵に含める場所として、モデル名へ混ぜる (`opus-5@keepalive`) / credential の
下に並べる / 別の器を立てる、が考えられるが採らない:

- **モデル名へ混ぜる** — 単価表を引く鍵がモデル名なので、混ぜた瞬間に引けなくなる。
  読む側が毎回 1 語を切り出して復元することになり、鍵が文字列の組み立てになる
  (stringly-typed)
- **credential の下 (モデルと同列)** — 素性はモデルと直交するので、同列に置くと
  「どのモデルの keepalive か」が取れない。単価はモデル依存なので、額も出せない
- **別の器 (`keepalive-counters/*.json` 等)** — DR-0027 以前の案。自送信が普通の
  1 本として usage に乗る以上、同じ数を 2 つの場所で数えることになる

いちばん内側に置くと、既に通っている道がそのまま使える。単価はモデルまでで
決まる (DR-0011「コストは読み出しのたびに計算する」) ので、**素性の段は単価の
計算に一切関わらない** — 素性ごとの額は、その素性の下にあるトークン数へ同じ
単価を当てるだけで出る。

### 素性の無い過去のファイルは `unknown` に寄せる

置き場には素性を知らない頃のファイルが残っている。`credential → モデル → 集計`
の形で、モデルの下にいきなり集計が置いてある。

読む側で `unknown` の 1 本にくるんで受ける。判別は**鍵の名前**で付く — 集計の器が
持つ鍵 (`requests` / `tokens` と旧形式の 4 区分) と素性の語 (`main` / `sub` /
`oneshot` / `codex` / `keepalive` / `unknown`) は重ならないので、どちらの形かは
中身を見れば決まる。

`Counters` の `Deserialize` が旧形式を吸収しているのと同じ流儀で、**読み込みで
だけ受けて書き戻しは新しい形**にする。1 度落とせばそのファイルは移行済みになる。

`0` でも「素性なし」の別語でもなく `unknown` に寄せるのは、これが既にある語
(`RequestOrigin::Unknown` = 「見分けが付かなかった」) そのものだから。過去の分に
ついて言えるのは正にそれで、新しい語を増やす理由がない。

### 報告は内訳を添える。合計の形は変えない

`/llm-gateway/stats` の JSON は、モデルの行 (`Entry`) に**素性ごとの内訳を足す**
だけにする。行そのもの (本数・区分ごとのトークン数・USD) は今までどおりの位置に
あるので、既存の読み手は壊れない。

内訳を出す / 出さないを問い合わせ (`?by=origin` 等) で切り替えない:

- 内訳の量はモデル 1 つあたり素性の数 (実測で 1〜2) で、応答が桁で伸びない。
  `?days=N` が上限を持つのは全期間が日数に比例して伸びるからで、事情が違う
- 切り替えを足すと、同じ口が 2 つの形を返すことになる。読み手は両方に備える

モデルの行が持つ数は、素性ごとの内訳の和と一致する (= 重複して持つ)。これは
1 日の合計 (`total_usd`) を内訳と別に置いてあるのと同じ形で、**よく見る数を
読み手に畳ませない**ため。

### CLI は `--by origin` で内訳を開く

既定は今までどおり `credential × モデル` の行。`--by origin` を付けると、内訳の
行が**素性ごとに割れ**、ラベルが `<素性> <credential> <モデル>` になる。素性を
先頭に置くのは、`keepalive` の行が縦に固まって読めるようにするため (見たいのは
「ping にいくら払ったか」で、その内訳としてモデルが要る)。

日ごとの合計行と全期間の合計行は**どちらの見え方でも同じ数**になる。割り方を
変えただけで、足した先は変わらない。

既定を内訳ありにしないのは、素性が 1 つしかない使い方 (gateway 越しに 1 つの
クライアントだけを通す) では行数が倍になるだけで何も増えないため。

## やらないこと

- **会話 (session) × モデルの粒度** — 別の要望 (issue
  `2026-09-07-stats-per-session-and-subagent`) があるが、軸の性質が違う。素性は
  語彙が閉じていて (6 語) 行数が増えないのに対し、会話の id は使うほど増える。
  日次ファイルの大きさと、過去日を読む速さに効くので、保存の形から別に設計が要る。
  本 DR では扱わない
- **素性ごとの単価** — 単価はモデルが決める。素性は同じモデルの中の内訳なので、
  当てる単価も同じ
- **素性ごとの結果 (cache に乗ったか / 乗らなかったか)** — 自送信が実を結んだか
  は知らせ (`/llm-gateway/events` の `cache`) の関心事で、トークンの積み上げとは
  軸が違う。stats に持たせると、1 本の結果を 2 か所で数えることになる
- **過去のファイルの書き換え** — DR-0011 のまま。読むときに `unknown` へ寄せる
  だけで、置いてあるファイルは触らない

## Alternatives Considered

**素性を日の直下 (credential の上) に置く** — `keepalive` の合計が 1 か所で取れる
形になる。採らないのは、いちばんよく見る数が「credential ごとにいくら使ったか」で、
そこへ辿るのに全素性を横断することになるため。内側に置けば、素性を見ない読み手は
今までどおりの深さで止まれる。

**素性を知らせ (events) の側だけで数える** — 既に流れているので追加が要らない。
採らないのは、知らせが**流れて消える**もので、購読していない間のことは残らない
ため。「いつ・どれだけ」を後から振り返るのが stats の役割 (DR-0011 の表)。
