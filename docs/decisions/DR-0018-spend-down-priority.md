# DR-0018: リセット間際の枠を優先して使い切る (spend_down)

- Status: Accepted
- Date: 2026-08-16

## 背景

サブスクの 7 日枠は**リセット時刻に未消費分が蒸発する**。使わずに残した分は
翌週へ繰り越されず、そのまま消える。DR-0015 で同格グループ内を「リセットが
近い順」に並べたが、あれはグループ内の話で、**グループをまたいで順位を
入れ替える手段が無い**。優先順の下位に置いた credential の 7d 枠がリセット
間際まで手つかずでも、上位が枯れない限り出番が来ない。

曜日・時刻の設定 (「毎週火曜の夜から使い切る」) は持たない。credential ごとに
リセット時刻はばらばらで、設定に曜日を書くと credential が増えるたび / 契約の
更新日がずれるたびに手で直すことになる。判定は**リセットまでの残り時間**で行い、
設定は「どれだけ手前から使い切りに入るか」の 1 つだけにする。

閾値を割合でも書けるようにするのは、**窓長にスケールさせる**ため。`25%` と
書けば 7d 枠なら 42h 手前、5h 枠しか持たない相手なら 1.25h 手前になる。
credential ごとに窓長が違っても 1 つの規則で表せる。絶対時間 (`40h`) は
「窓長に関係なく、この時間を切ったら」と言いたいときに使う。

## 決定

### 1. routing rule に `spend_down_within` を足す

```toml
[[ns.personal.routing]]
models = ["claude-fable-*"]
routes = ["claude-zunsystem", "claude-kawazzz", "bedrock"]
# 最長周期枠の窓長の 25 % 以内にリセットが迫った credential を先頭へ繰り上げる。
spend_down_within = "25%"
# 絶対時間でも書ける。
# spend_down_within = "40h"
```

- 値は文字列。`<数>%` なら**窓長に対する割合**、それ以外は humantime 形式の
  **絶対時間** (`40h`, `2d`, `90m`)
- 書かなければ従来どおり (昇格しない)。`routing` 規則ごとに書く — モデル群に
  よって使い切りたい相手が違うことがある
- 形式不正 (`25x`, `%`, 範囲外の割合) は設定読み込み時にエラー。ただし
  **絶対時間が対象 credential の窓長を超えていても起動時エラーにしない** —
  窓長は実行時に upstream から聞いて初めて分かるので、設定の検査では判定
  できない (常に昇格することになるが、それは書いたとおりの動作)

### 2. 見るのは各 credential の**最長周期の枠だけ**

5h 枠は数時間で回るので、残り僅かを昇格の理由にすると常時昇格しているのと
変わらない。使い切り戦略の対象は「蒸発すると痛い長周期枠」に限る (DR-0015 で
7d 窓だけを見たのと同じ理由)。

「最長周期」は窓長 (`window_seconds`) の大きい方で決める。`5h` / `7d` の欄名で
決め打ちしない — provider によって欄の意味が違う (codex の `secondary` が
7d 相当) ので、期間そのもので比べる。

### 3. 昇格はリストの先頭へ、affinity より下位

順序決定は 3 段構えになる:

1. `routes` の静的順 + 同格グループ内の動的順 (DR-0015)
2. **spend_down 昇格** — 閾値内の credential を**リスト先頭へ移動**。複数
   該当するならリセットが近い順。該当しない残りは 1. の順のまま
3. session affinity の先頭寄せ (DR-0009)

**affinity が最上位**なのは、会話の途中で credential が変わると prompt cache が
切れるため。使い切りで得る枠より、切れたキャッシュを積み直す消費の方が大きい。
新しい会話は 2. の順で入るので、使い切りは会話の切れ目から効き始める。

### 4. リセット時刻か窓長が取れない credential は昇格しない

静的順のまま据え置く。「取れない = 期限が近いかもしれない」と推測して繰り上げると、
観測できていない相手を根拠なく最優先にすることになる。DR-0015 が「7d reset を
読めない候補は読めた候補の後ろ」としたのと同じ扱い方 (推測で順位を動かさない)。

### 5. 残量は見ない

「リセットが近いが既に使い切っている」credential を先頭に置いても、枯れていれば
429 が返り、既存の denial → fallback (DR-0009) が次へ流す。残量を条件に足すと、
観測が古い credential で「残っているはず」の誤判定が入る。安全弁は既にある。

### 6. 窓長を core の形に足す

[`crate::quota::Window`] と [`crate::quota::QuotaLimit`] に
`window_seconds: Option<u64>` を足す。**どちらの周期かを provider が申告する**
形にして、core は大小を比べるだけにする (DR-0014 §3)。

- anthropic: 応答ヘッダの `5h` / `7d` 系列名、枠照会 API の `limits[].kind`
  (`session` = 5h 系 / `weekly_*` = 7d 系) から既知の周期を導出する。対応表は
  preset の中に閉じる
- openai: 応答ヘッダの `x-codex-<窓>-window-minutes`、枠照会 API
  (`wham/usage`) の `limit_window_seconds` を読む

## 採らなかった案

- **曜日・時刻での指定**: credential ごとにリセット時刻が違い、契約更新でずれる。
  設定が実態に追従しなくなる
- **割合指定だけ / 絶対時間指定だけ**: 割合は窓長にスケールする利点があるが
  「窓長に関係なく残り 40h を切ったら」を表せない。逆も同じ。両方を 1 つの欄で
  受けるのは、書き分ける対象が同じ「閾値」1 つだからで、欄を 2 つにすると
  両方書かれたときの意味を決める必要が出る
- **枠照会 API (`QuotaApi`) の結果だけを判定の入力にする**: 枠照会は既に締め出
  されている経路にしか走らない (`claim_probe`)。健全な credential では一度も
  聞かないまま終わるので、判定材料が永久に埋まらない。転送のついでに読める
  応答ヘッダ (`Metering` → `Snapshot`) を主にし、DR-0015 と同じ入力で動かす
- **昇格した credential をグループ内に留める**: グループをまたげないと、下位
  グループの credential を使い切れない。今回の動機そのものが満たせない
- **affinity より昇格を優先する**: 会話の途中で credential が切り替わり prompt
  cache が切れる。使い切りで拾う枠より積み直しの消費が大きい
