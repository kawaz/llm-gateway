# DR-0006: 既定 namespace を特別扱いせず、`/v1` を `/ns-default` へ内部ルーティングする

- Status: Active
- Date: 2026-07-29

## Context

`/v1/messages` のように namespace を書かないパスは、いま `Config` の
`#[serde(flatten)] default_namespace: Namespace` に解決される。つまり **config の
トップレベルがそのまま既定 namespace の定義**になっている。

この形が 2 つの問題を生んでいた。

### 認証をかけ忘れても誰も気づかない

`Namespace::accepts()` は `auth_token` が未設定なら無条件で通す。

> 設定に書いていなければ誰でも通す。127.0.0.1 で待ち受けている前提で、
> 同じマシンの他プロセスと区別したいときだけ書く。

この前提は前段に Caddy を置いた時点で崩れた。名前付き namespace
(`ns.personal` / `ns.emrd`) には `auth_token` を書いたが、トップレベルには
書いていなかったため、**`/v1/messages` が認証なしで外から叩ける**状態になっていた。

canddy 側のセッションが実機で確認済み (2026-07-28)。Authorization ヘッダを
付けずに POST して 200 が返り、課金が発生した。到達元は tailnet で、
参加デバイスには公開 IP を持つクラウドホストが複数含まれる。

「書かなければ通す」という fail-open が、公開経路の追加という**設定ファイルの外**で
起きた変化によって穴に変わった。設定を 1 行足せば塞がるが、次に namespace を
足す人が同じ穴を開けられる構造は残る。

### 設定が二重管理になる

トップレベルに `[filter]` `[[routing]]` `[aliases]` があり、`[ns.personal]` にも
同じ種類の設定が並ぶ。単一用途なら namespace を意識せずに済むという当初の狙いは、
namespace を使い始めた時点で「同じことを 2 箇所に書く」に変わっていた。

## Decision

**gateway の機能はすべて namespace 配下のパスとして定義する。** namespace を書かない
パスは、その先頭に `/ns-default` を補ったものとして解決する。

```
/v1/messages  →  /ns-default/v1/messages
/v1/models    →  /ns-default/v1/models
```

**`/v1` の下が丸ごと namespace の下に入る**のであって、`/v1` が `/ns-default` に
置き換わるのではない。

`default` は名前付き namespace の 1 つになり、特別扱いしない。トップレベルの
`#[serde(flatten)] default_namespace` は廃止し、`[ns.default]` として他と同じ書式で書く。

kawaz 裁定 2026-07-28:

> トップのヘルスチェックとか以外は自動で /ns-default 内部ルーティングされるで良いでしょう。
> その方が色々整理がしやすい。

> 要はヘルスチェックとか llm ゲートウェイ機能のパスは全て ns 配下に役割を移動するということです。

### `ns.default` が無ければ 404

`[ns.default]` を config に書けば `/v1/...` が使え、書かなければ 404 を返す。
それだけ。**委譲 (`default` → `personal` のような転送) は持たない。**

> default→personal なくて良いや。
> そして ns の設定なければ deny または 404 でいいんじゃね。

「名前を明示したリクエストしか受けない」構成は `[ns.default]` を書かないことで実現でき、
拒否のための専用の書き方 (deny-all) は要らない。委譲を持たないので循環検出も不要になる。

既存の `namespace_of()` は `/v1/...` に対して `default` を返し、未定義の namespace には
`unknown_namespace()` が 404 を返す。**この挙動がそのまま仕様になる。**

### `auth_token` 未設定は「誰も通さない」

`accepts()` を fail-open から **fail-closed** に反転する。`auth_token` が未設定の
namespace は、トークンの有無にかかわらず通さない。**書き忘れたら通る、を無くす。**

> それとも必須にしとくか? その方が面倒ないか

元の設計は「127.0.0.1 で待ち受けている前提だから書かなくてよい」だった。前段に Caddy を
置いた時点でこの前提が崩れ、既定 namespace が認証なしで外から叩ける状態になっていた
(実際に課金が発生したことを実機で確認済み)。fail-open が**設定ファイルの外で起きた変化**に
よって穴に変わった形で、同じことは名前付き namespace の書き忘れでも起こりうる。

`[ns.default]` を書かなければ 404 になったことで「**書く = 使う意思がある**」が成立する。
そこに認証も書かせれば、書き忘れの穴が消える。

**型は `Option<String>` のまま**にして、deserialize は通す。

> 起動エラーはやめて下さい。アクセス時エラーで良い

必須フィールドにすると、1 つの namespace の設定漏れで gateway 全体が起動できなくなる。
他の namespace は正常に使えるべきなので、弾くのはアクセス時にする。影響がその namespace
だけに閉じる。

エラー文言は「トークンが違う」と「`auth_token` が設定されていない」で分ける。同じ文言だと、
正しいトークンを送っている利用者が原因に辿り着けない。
認証は「どう構成するか」の結果として付いてくる。

### トップレベルを空けると、管理用の口を置ける

LLM を中継する機能をすべて namespace の下へ移すと、トップレベルのパス空間が空く。

> 例えば統計情報やログや現在の設定を見たり管理したりする管理コンソールの役割も
> ns 以外でかつ llm ゲートウェイと被らないパスに持ちやすくなります。

`/v1/...` がトップに居座ったままだと、管理用のパスを足すたびに「これは中継の口か
管理の口か」を考えることになり、将来 upstream 側の API が増えたときに衝突もしうる。
`/healthz` を namespace の外に置いたのは、その最初の 1 つでもある。

### 外から見える形は namespace 配下のパス空間

> ns-*/ が cc から見た base_url 本体で、トップも基本は全て default に内部ルーティング
> されるので ns-*/ 内のルーティングが外見という感じです。

クライアントが `ANTHROPIC_BASE_URL` に置くのは `https://<host>/ns-<name>` であり、
その下のパス構成が gateway の公開仕様になる。トップレベルの `/v1/...` は
`default` への糖衣であって、独立した仕様ではない。

### 死活監視の口

`/healthz` は前段のロードバランサが数秒ごとに叩く。認証も credential も要らない。
業務のエンドポイントを死活監視に使うと、そのエンドポイントの認証方針が監視側に
縛られる (実際 `/v1/models` を監視に使っていたために、既定 namespace に認証を
かけると監視が 401 で落ちて全断する状態になっていた)。

**`/ns-<name>/healthz` は作らない。** namespace の下は upstream の API 仕様が
そのまま入る空間で、gateway が独自のパスを生やす場所ではない。

> `/ns-<name>/healthz` は存在しないが正しいです。llm ゲートウェイの仕様として
> 存在するとしたら別ですが。逆にもし claude の base_url が healthz を使い始めた
> とした場合は、こちらのヘルスチェック用のパスを別に避難する必要があります。

この非対称性が起点になった。**衝突したときに動かすのは常にこちら側**で、upstream の
API 名は向こうが決めるので譲れない。トップレベルに `/healthz` を裸で置くと、
upstream がその名前を使い始めたときに避難が要る。

### gateway 自身の機能は `/llm-gateway/` の下にまとめる

> そう考えると /llm-gateway/healthz をヘルスチェックパスとして、新機能を作る場合も
> 全て /llm-gateway/ に置くことにすれば、それ以外を全て ns-default にルーティング
> という簡潔にできそうですね。

判定ルールが 1 本になる。

```
/llm-gateway/...  →  gateway 自身の機能 (死活監視・統計・設定閲覧・管理コンソール)
それ以外          →  /ns-default/... へ内部ルーティング
```

利点が 3 つある。

- **衝突が原理的に起きない。** upstream の API が `/llm-gateway/` を使うことは考えにくく、
  避難の想定自体が不要になる。前節の非対称性が問題として消える
- **新機能を足すたびに考えなくてよい。** `/llm-gateway/` の下に置く、で終わる
- **パスの解釈が一意になる。** `/llm-gateway/` 以外はすべて namespace の下の話になり、
  「これはどちらの口か」を考える場面が消える

なお「未知のパスを upstream へ素通しする」ことは**しない**。転送の経路選択はボディの
`model` フィールドが起点で (alias 解決と credential 選択に使う)、パスだけでは
どの upstream へ送るかを決められない。`model` を持たない新 API を通したくなったら、
そのとき経路選択の設計から考える。

`/healthz` (トップレベル) は `/llm-gateway/healthz` へ移す。実装済みだが稼働プロセスには
未反映なので、移行による影響はない。

## 移行

既存の config はトップレベルに設定を持ち、`auth_token` も無いので、そのままでは
読めなくなる。`[ns.default]` へ移し、各 namespace に `auth_token` を書く作業が要る。

稼働中は 8401 (stable, Homebrew 版) と 8402 (unstable, ローカルビルド) の 2 つ。
Caddy が 8402 → 8401 の順にフォールバックするので、**先に 8402 だけ入れ替えて確認し、
問題なければ 8401 を上げる**。片方が古い形式のまま動いていても、config は別ファイルなので
互いに影響しない。
