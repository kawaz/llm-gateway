# 枠ごとの利用率の推移を、1 % 動くたびに 1 行・その間に流したトークンをモデル別に添えて貯める

## 概要

credential ごと・枠ごと (5 時間 / 7 日の窓、枠照会 API が返すモデル別の枠など) の利用率が動くたびに 1 行を追記で残し、その行に「前にその枠が動いてから今回までに、この gateway がその credential で流したトークン量」をモデル別に添える。1 % あたりにどのモデルで何トークン使ったかを、行から直接読めるようにする。

設計の正本は [DR-0044](../decisions/DR-0044-usage-history-per-window.md)。

## 背景

外部で「Fable は Opus より、定額プランの枠を API 換算額あたり数倍速く減らす (cache read の計上が非対称)」という主張が出た。kawaz は眉唾と見ていて、手元の実データで確かめたい。

- 日次のトークン量は日次集計 (DR-0011、`<[stats] dir>/<日付>.<書き手>.json`) に credential × モデル × 区分で残っている
- 枠の利用率は `usage-latest.<書き手>.json` (DR-0007) に最新の 1 つが上書きされるだけで、推移が残らない。ログにも出ていない

両者を突き合わせるには、利用率の推移と、その区間に流したモデル別の量が対で要る。

## 取れる枠 (2026-11-17 に実装を読んで確認)

| 経路 | 枠 | いつ取れるか |
|---|---|---|
| 応答ヘッダ (Anthropic の `anthropic-ratelimit-unified-*`) | `5h` / `7d` の窓 (`utilization` 0.0〜1.0、1 % 刻み) | 転送の応答のたび (`usage?refresh=true` の最小リクエストも) |
| 応答ヘッダ (Codex の `x-codex-{primary,secondary}-*`) | primary / secondary の窓 (スナップショットの欄名は `5h` / `7d` だが周期は `window_seconds` が言う。実測では primary が 7 日) | 転送の応答のたび |
| 枠照会 API (Anthropic の `/api/oauth/usage`) | `session` / `weekly_all` / `weekly_scoped` (モデル別、例: Fable) など upstream が返す全部 (`percent` 0〜100) | 聞きに行った時だけ: `usage?refresh=true`、`pace_cap` の経路で枠が読めていない時、締め出し中の経路の裏の照会、定期の照会 (前の周期から流した credential だけ、既定 5 分ごと) |
| 枠照会 API (Codex の `wham/usage`) | primary / secondary | 同上 |

取れないもの:

- **モデル別の枠は応答ヘッダに出ない** (実測 2026-07-31、DR-0009)。枠照会 API の定期照会 (DR-0044 決定 9) で、流している間は周期 (既定 5 分) ごとに取る
- overage (従量への切り替えの可否) は利用率ではないので行にしない
- Bedrock は使用量を取れない (DR-0007)

手元の観測 (2026-11-17) では、Anthropic の credential のうち一部はヘッダに `5h` の窓を出さず `7d` だけを返していた。その credential では応答ヘッダからは `7d` の系列だけが残る。

## 決めたこと (詳細は DR-0044)

- 置き場: `<[stats] dir>/usage-history/<YYYY-MM-DD>.<書き手>.jsonl`。日付は観測時刻の地方時、書き手は待ち受け先 (日次集計と同じ)。1 行 1 件の JSON で追記のみ
- 1 行の種類: `start` (このプロセスがその枠を初めて見た起点、トークンは添えない) / `step` (利用率が上がった。`from` / `since` / `tokens`) / `rollover` (窓が切り替わったか値が下がった。差は添えず起点を置き直す)
- 値が変わらない観測は行にしない。リセット時刻だけの揺れも、前のリセット時刻を過ぎていなければ行にしない
- トークンは日次集計の器 (`Stats`) がプロセス起動から積んだ累計の差。モデル別、素性 (main / sub / keepalive …) は合算、区分は日次集計のファイルと同じ (upstream が言った数のまま)
- 書き込みは日次集計と同じ 60 秒の保存の周回と終了時。best-effort (落とし損ねた行は次の周回で書き直す、転送は止めない)
- 古い日のファイルは消さない (日次集計と同じ。作り直せない記録で、量の見積もりは DR-0044 決定 6)
- DR-0031 の 4 つの意味論では (3) の仲間 (書き手ごとに自分の分だけを書き、読む側が合わせる。合わせ方は行の和集合)。新しい trait は切らず、汎用層に `gateway_core::daily_log::DailyLog` を置いた
- モデル別の枠を密に取るため、枠照会 API を周期ごとに聞く (kawaz 裁定 2026-11-21、DR-0044 決定 9)。聞くのは前の周期で聞けてから流した credential だけ (判定は起動からの累計の本数)、credential ごとに 1 回。答えは推移とスナップショットの穴埋めに流し、締め出しの印は作らない (DR-0009)。兄弟のプロセスとは譲り合わない (譲ると譲った側の系列が疎になる)。失敗は次の周期で聞き直し、続けば 1 時間まで倍々に空け、429 は 1 時間控える。`[stats] quota_poll_interval` (既定 `5m`、`0` で止める、それ以外は 1 分以上)

## 記録の限界

- **gateway を通らない利用は数えられない**。同じ credential を別のマシン・Web・gateway を通さない CLI から使った分は利用率を動かすが、トークンには現れない。その区間の 1 % あたりの量は実際より少なく見える
- **兄弟のプロセス (stable / unstable) は自分が流した分しか知らない**。各プロセスは自分のファイルに自分の増分を書き、読む側で合わせる。これで足りるかの判断:
  - 1 つのプロセスだけが流していた期間は、行をそのまま 1 % あたりの量として読める
  - 両方が流していた期間は、行単位の直読みはできない (各プロセスの区間の境目が揃わない。同じ 1 段を両方が `step` として書くこともある)。期間 [t0, t1] で合わせる: 利用率の増分は全書き手の行を時刻で並べた値の差 (段の数を行の数で数えない)、トークンは全書き手の `step` の `tokens` の和。境目で各書き手 1 段ぶんの誤差が残るが、数時間〜日の期間なら効かない
  - 書き手をまたいで今の区間を共有する仕組み (flock で調停する共有の累計) は採らない。DR-0011 と同じく、排他が要る状態そのものを作らない方が単純
- **応答 1 本ぶんのずれ**: 利用率は応答ヘッダが届いた時点、トークンは本文を読み終えた時点で数えるので、1 本の応答のトークンはその 1 本のヘッダで動いた段ではなく次の段に入る (upstream がヘッダの利用率にその 1 本を含めているかは確かめていない)。区間の境目が 1 本ぶん後ろへずれるが、並べて読めば打ち消し合う。並行して流している時は、どの 1 本がどの段に効いたかの対応はもっと緩む
- `usage?refresh=true` の最小リクエスト (haiku、数トークン) は日次集計に積まれないので、`tokens` にも入らない

## 起点の扱い

- **起動直後**: 最初に見た値で `start` を書き、そこから数える。起動前に流した分は数えていないのでトークンは添えない。前のプロセスの最後の値は起点にしない (停止中の動きが起動後のトークンに付くため)。再起動の前後で区間は途切れる
- **窓の切り替わり**: 前に見たリセット時刻を過ぎた観測でリセット時刻が変わったら `rollover`。切り替わりをまたぐ区間は前の窓の分と新しい窓の分が混ざるので、差は添えない。利用率が下がった観測も `rollover`
- **枠照会 API でしか取れない枠** (モデル別の枠): 起点はその枠を初めて聞けた時。それより前に流した分は、その系列には入らない

## 既存 issue との関係

[plan command — routing 解決 + quota forecast](2026-09-17-plan-command-routing-and-quota-forecast.md) (残量予測) の基盤になる。あちらは「履歴不要の形」(窓の経過 % と使用 % の対) でスコープを切っているが、消費の速さ (1 % あたりの時間・トークン) を過去から推定する予測に進む時は、この推移が入力になる。
