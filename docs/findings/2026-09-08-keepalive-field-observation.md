# keepalive の実運用観測 (DR-0024 導入前後、日次 stats)

DR-0024 の cache 戦略 (main = `keepalive` = 常時 1h + 55 分 refresh ping) が
実運用で効いているかを、日次 stats (`/llm-gateway/stats`) の実測で評価した。
設計の根拠と分岐点の計算は DR-0024 §3、導入前の費用構成は
`2026-09-03-prompt-cache-investigation.md` が正本。

## 判明した事実

### 効いている (read 正規化で 1/5、ping 補正後は約 1/4.9、write+延命費用の項で約 1/3.9)

`claude-fable-5-1` (= main セッションが載るモデル) の導入前 2 日 / 導入後 5 日
を全 credential 合算で比べると、**read 1M トークンを維持するのに要した write 費用**が
$0.759 → $0.152 に落ちた (5.0 分の 1)。read の量はむしろ 2.6 倍に増えている
(573.9M → 1478.8M) ので、「使わなくなったから安くなった」ではない。

| | req | write | read | $write | $read | $合計 | write 比 | $/req | $write/1M read |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 導入前 (09-02〜03) | 1,259 | 34.8M | 573.9M | 435.45 | 143.47 | 604.88 | 72.0% | 0.480 | 0.759 |
| 導入後 (09-04〜08) | 3,330 | 14.9M | 1478.8M | 225.51 | 369.69 | 672.03 | 33.6% | 0.202 | 0.152 |

- **費用の支配項が write から read へ移った** (72.0% → 33.6%)。DR-0024 が狙った
  「5 分失効後の全量再構築を無くす」がそのまま数字に出ている
- リクエスト単価は $0.480 → $0.202 (2.4 分の 1)。1 リクエストあたりの read は
  308〜524k → 409〜497k とほぼ横ばいで、prefix が縮んだわけではない

ただし **この read と write には ping 自身のぶんが混ざっている** (ping は普通の 1 本として
stats に入る)。ping のトークンを stats から差し引き、ping 費用 (read だけでなく
write / input / output も含めた総額) を延命費用として費用側に立てると:

| | 実 read | $実 write | $ping | $実write/1M 実read | $(実write+ping)/1M 実read |
|---|---:|---:|---:|---:|---:|
| 導入前 (09-02〜03) | 547.8M | 397.78 | 44.84 | 0.7261 | 0.8080 |
| 導入後 (09-04〜08) | 1307.3M | 194.38 | 77.85 | 0.1487 | 0.2082 |

- **ping 補正後は 4.88 分の 1** ($0.7261 → $0.1487)。ping の read は導入後 5 日で
  171.5M = 見かけ read の 11.6% で、補正しても桁は動かない
- **延命費用を費用側に立てても 3.88 分の 1** ($0.8080 → $0.2082)。fable の ping
  354 回で $77.85 (1 回あたり $0.220) は、消えた write の前では小さい
- 同じ実 read 1307.3M を導入前の単位費用で賄うと $1,056.24。実 write $194.38 +
  ping $77.85 = $272.23 なので、**5 日で純減 $784** (ping 費用を差し引いた後)

### ping 費用が節約を食い切るモデルがある (opus-5)

同じ補正を全モデルにかけると、モデルによって結論が変わる:

| モデル | 実 read (後) | ping 回数 (後) | $ping | $/ping | $w/1M実read 前 → 後 | write のみ | write+ping | 5 日の純減 |
|---|---:|---:|---:|---:|---|---:|---:|---:|
| `claude-fable-5-1` | 1307.3M | 354 | 77.85 | 0.220 | 0.7261 → 0.1487 | 4.88x | **3.88x** | +$784.01 |
| `claude-opus-5` | 931.2M | 239 | 67.45 | 0.282 | 0.3377 → 0.2753 | 1.23x | **0.97x** | **-$9.36** |
| `claude-sonnet-5` | 673.1M | 1 | 0.10 | 0.098 | 0.3205 → 0.2038 | 1.57x | **1.59x** | +$80.34 |

- **`opus-5` は ping 補正後に改善が消え、わずかに赤字**になる (1.23x → 0.97x、
  5 日で純減 -$9.36)。理由は 2 つ重なる: (a) opus は read 単価が input の 0.1 倍
  = 分岐比 20 倍しかないので ping 1 回が相対的に高い ($0.282/回、fable の 1.3 倍)、
  (b) opus は subagent が支配的で、少数の main 系列を延命するために払う ping が
  節約した write を上回る。09-06 だけで opus に 178 回 / $52.18 が出ている
- `sonnet-5` は ping が実質 1 回しか観測されず、1.57 分の 1 がほぼ丸ごと残る
- **fable / sonnet の黒字 ($864) が opus の赤字を大きく上回る**ので、全体では黒字
  (5 日で純減 約 $855)。ただし opus の `keepalive_horizon = 0.3` (= 5.5 時間) は、
  この 5 日を見る限り **短くする方向に見直す余地がある**

### 介入が main だけで足りる、が数字で裏付いた

`ephemeral_1h` / `ephemeral_5m` の内訳が取れる 09-06 以降で、モデルごとの
1h write 比率が大きく違う:

| モデル | 1h write 比率 (09-06〜08) | 解釈 |
|---|---:|---|
| `claude-fable-5-1` | 100% (2.13M/2.13M、09-08) | main が載るモデル。全て 1h 戦略下 |
| `claude-sonnet-5` | 48〜67% | main と sub が混在 |
| `claude-opus-5` | 0〜14% | ほぼ subagent (= `passthrough` の 5m) |

`opus-5` は worker 用途が支配的で、DR-0024 の「sub は passthrough」がそのまま
効いている。改善幅も main 系ほど大きくない ($write/1M read が 0.338 → 0.242、
sonnet は 0.323 → 0.204)。導入前調査の「費用の 9 割は main」と整合する。

### ping の実回数と単価 (セッション jsonl から実測)

gateway 側に発火履歴が残らないので、**セッション jsonl の user 側 marker から数えた**
(手順は「検証の詳細」)。数える単位は「注入された marker 1 件」であって応答の中身では
ないので、marker を拒否・無視した応答もリクエストとして計上される。
導入後 5 日 (JST) で 594 回・read 310.6M・$145.40:

| 日 (JST) | 09-03 | 09-04 | 09-05 | 09-06 | 09-07 | 09-08 |
|---|---:|---:|---:|---:|---:|---:|
| ping 回数 | 43 | 84 | 91 | 294 | 62 | 63 |
| $ping | 46.04 | 31.76 | 14.60 | 73.54 | 9.72 | 15.78 |
| nonce 遵守率 | 32.6% | 73.8% | 95.6% | 96.9% | 100.0% | 98.4% |

- 導入後 5 日の内訳は `fable-5-1` 354 回 / `opus-5` 239 回 / `sonnet-5` 1 回
  (導入前の 09-03 は fable 42 回 + sonnet 1 回)
- **ping 1 回の実費は fable $0.220 / opus $0.282** (導入後 5 日の平均)。
  DR-0024 の週次試算が置いた $0.1 より**どちらも高い**。定常状態の日 (09-05 / 09-07)
  では fable $0.104 / $0.157 と試算どおりだが、cache が消えてから marker が届いた日
  (= `late`、全量 write を伴う) が平均を押し上げている
- **09-03 の $1.068/ping は異常値**。まだ 1h 戦略が効いていない時期に marker が
  届き、5 分で消えた cache を毎回 1.89M トークンぶん書き直している。
  DR-0024 の不採用案「マーカーだけ 1h」の症状そのもので、**1h 本体と ping が
  揃って初めて成立する**ことの実地の裏付けになっている
- 1h write は fable $20/MTok なので read との比は 80 倍。DR-0024 §3 の
  「5.1 系 80 回 ≈ 73.3 時間」「horizon 0.3 → 22 時間」の前提は単価表
  (`preset/pricing.rs`) と一致していて、設定値 (`keepalive_horizon = 0.3`、
  personal / bare / 業務面の 3 namespace) も設計どおり入っている

**nonce 遵守率は費用と無関係** (marker が届いた時点でリクエストは発生し、cache も
繋がる) だが、webui のノイズ量の指標になる。32.6% → ~98% への改善は、
合言葉だけを返させる常時ロードのルールが 09-04 に入った時期と一致する。
遵守しなかった応答も延命そのものには効いている。

### 副作用は観測範囲では出ていない

- **停止の残留なし**: 両プロセスの `GET /llm-gateway/keepalive/paused` が
  ともに空。置き場のファイルにも `paused` は 0 件。ログに残る pause は 1 セッション
  分だけで、いずれも数秒以内に実リクエストで resume されている
  (DR-0024 §2「解くのは実リクエスト 1 本だけ」が実際に働いている)
- **1h write の連発なし**: 導入後の write 総量はむしろ減っている。「マーカーが
  毎回 2 倍で書き直す」不採用案の症状 (read 数万 / write 数十万) は出ていない
- **多プロセスの重複なし**: 現時点の見張りは 11301 に 15 系列 / 11302 に 1 系列で、
  同じ `(session_id, prefix)` の重複は無い。ping 回数も 0〜5 回に収まっていて、
  55 分刻みの範囲を超えていない
- **設定漏れの検出は働いた**: 09-04 04:47Z の 1 回だけ
  `cache keepalive needs a webhook destination; no signal will be sent` が出ている。
  この起動では ping が出ていない (= 1h 戦略のみ) はずで、DR-0024 §2-6 の
  警告が意図どおり鳴った例

## 実用的な示唆 / ベストプラクティス

- **導入日は 09-04 (JST)**。keepalive の見張り復元ログの初出が 2026-09-03T17:01Z。
  日次 stats でも `fable-5-1` の read/write 比が 09-03 の 15.7 から 09-04 に 70.0 へ
  跳ねていて、境界がはっきり出る
- **`ephemeral_1h` / `ephemeral_5m` の内訳が stats に入ったのは 09-06 から**。
  09-04〜05 の 2 日は「1h が効いていたことは read/write 比から分かるが、
  内訳では確認できない」。導入前後の厳密な内訳比較をしたい場合はこの穴を意識する
- **1h write 比率はモデル単位の main/sub 混在度の指標として使える**。
  `cache_strategy` を per-request に持たなくても、日次 stats だけで
  「どのモデルが main 用途か」が読める
- 評価指標は「write 総額」でなく **`$write` ÷ (read − ping read)** を使う。
  稼働量が日ごとに 10 倍近く振れるので総額では前後比較にならず、かつ ping 自身の
  read が分母を 11.6% 水増しするので、ping を抜かないと改善を過大評価する
- **ping 費用はモデル単位で評価する**。read 単価が input の 0.025 倍 (5.1 系) か
  0.1 倍 (それ以外) かで ping 1 回の実費が 4 倍違い、5.1 系で成立する
  `keepalive_horizon = 0.3` が他モデルでは赤字に転じうる

## 結論

**効いている (ping 補正後も)。** ただしモデルによって収支が違い、削減額の絶対値は推測。

- 確定: main が載るモデル (`fable-5-1`) で write の費用比が 72% → 34% に落ちた。
  ping のトークンを分母から抜いても実 read 1M あたりの write 費用は
  $0.7261 → $0.1487 (4.88 分の 1)、ping 費用 (read だけでなく write / input /
  output も含む総額) を費用側に立てても $0.8080 → $0.2082 (3.88 分の 1)。
  read 量は増えているので稼働減が原因ではない
- 確定: **`opus-5` では ping 費用が節約を食い切り、わずかに赤字**になる
  (write のみ 1.23x → write+ping 0.97x、5 日で純減 -$9.36)。全体では
  fable / sonnet の黒字 ($864) がこれを大きく上回るので黒字 (5 日で約 $855) だが、
  opus の horizon は見直し候補
- 確定: 停止の残留・1h write の連発・多プロセス重複といった副作用は、
  現時点の置き場とログの範囲では観測されない
- 推測: 「5 日で純減 $784 (fable)」は、導入前の単位費用を導入後の実 read 量に
  当てた外挿。次の 3 点が交絡する:
  1. **ping 回数は下限**。marker 基準にしたことで拒否・無視した応答は拾えたが、
     走査対象 (`~/.claude*/projects/`) の外にある設定ディレクトリのセッションは
     数えられない。`sonnet-5` は置き場で 7 本の系列が見張られているのに ping が
     2 回しか観測されておらず、取りこぼしを疑う根拠になる
  2. **導入前 2 日のうち 09-03 に既に 43 ping が出ている** (導入日は 09-04 だが
     見張り自体は 09-03T17:01Z から動いていた)。しかも 1h 戦略が効く前なので
     1 回 $1.07 と極端に高く、導入前の基準値を押し上げている
  3. **単価が 5.1 系のもの**。09-02 に `fable-5` → `fable-5-1` へ移って cache read
     単価が 1.0 → 0.25 に下がっており、導入前サンプル 2 日はこの移行直後に当たる。
     加えてセッションの長さ・並列度が日ごとに違う。09-08 は集計時点でまだ
     稼働中の日なので、その日の値は確定値ではない

  桁 (数百ドル/週) は信じてよいが、金額そのものは幅を持って読む

### データ不足 — 決着させるなら足す計測

1. **ping の発火回数と結果の内訳** (issue: `keepalive-daily-counters`)。今回は
   jsonl 走査で代替したが、これは**今回限りの遡及手段**で正本ではない。gateway の
   外の成果物 (セッションログの形式・置き場) に依存していて、走査対象外の設定
   ディレクトリを取りこぼすうえ、`applied` / `late` / `foreign` の別が取れないので
   「期限内に間に合ったのか (`late` = cache が消えてから届いた = 払い損)」が分からない。
   日次 stats と同じ流儀で `<stats dir>/keepalive-counters/<待ち受け>.json` に
   日別の {出した数, applied, late, foreign, 出したが戻らなかった数, トークン内訳}
   を積めば、ping 費用の実額と収束の健全性 (`foreign` の多さ = 重複) が両方取れて、
   jsonl 走査という外部依存も要らなくなる
2. **ping トークンを stats 側で分離する**。ping も普通の 1 本として stats に入るため、
   今回は jsonl から数えた ping トークンを手で引いている。トークン種別に keepalive 印を
   足せば、`$実write ÷ 実 read` が stats だけで出せる
3. **horizon の事後評価**。「ping を出した系列のうち、実際に会話が再開したのは
   何割か」が取れると、0.3 が高すぎ / 低すぎの判断ができる。1 の履歴に
   「この系列は最終的に実リクエストで再開したか」を足すのが最小の形。
   **`opus-5` の赤字を踏まえると、これは最優先**: 再開率が分かれば
   「5.1 系以外は horizon を下げる」の判断が数字でできる

### ping の数え方 (jsonl 走査、user 側 marker 基準)

**この jsonl 集計は今回限りの遡及手段**で、正本は gateway 側の日別カウンタ
(issue: `keepalive-daily-counters`)。gateway に発火履歴が無い間の代替にすぎない。

`~/.claude*/projects/*/*.jsonl` を走査 (3,635 ファイル)。各行を JSON として読み:

1. `type == "user"` で本文 (text / content ブロック) に `[llm-gateway keepalive ping]`
   または `LLMGW-KEEPALIVE-` を含む行を **ping の発生点**とする
2. 同じファイル内でその次に現れる `type == "assistant"` 行を、その ping の応答とする。
   次の `user` 行に当たったら打ち切る (ping 起因で tool を呼んだ 2 通目以降は含めない)
3. 応答を `(JST 日, message.id)` でユニーク化し、その `usage` の
   `input_tokens` / `output_tokens` / `cache_creation_*` / `cache_read_input_tokens` を
   `message.model` の単価で USD 化する

**数える単位を assistant 応答の nonce にしてはいけない** — marker を拒否・無視した
応答でもリクエストは発生していて課金される。旧集計 (nonce 基準) は導入後 5 日で
556 回だったが、marker 基準では 594 回で、**約 6% を取りこぼしていた**。

**JST で日を切る**。jsonl の `timestamp` は UTC、日次 stats は JST 日で 1 ファイル
なので、UTC のまま突き合わせると 9 時間ぶんずれる。窓全体の合計はほぼ変わらないが、
日別の内訳は大きく変わる (例: 09-06 は UTC 基準 146 回 → JST 基準 294 回)。

**message.id でのユニーク化は必須** — streaming 途中の中間値で同じ `message.id` の行が
複数回出る (導入前調査の「dedupe して最後の値を採る」と同じ罠)。usage はその
`message.id` について最後に現れた値を採る。

### ping 補正の計算

ping のトークンを stats のトークンから種別ごとに差し引いてから**同じ単価表で**
USD 化する (両側の単価が食い違わないようにするため)。ping 費用は read だけでなく
write / input / output も含めた総額。導入前の単位費用を導入後の実 read に当てたものを
反実仮想とする。

| モデル | 実read 前 | 実read 後 | $w/M実read 前 → 後 | $(w+ping)/M実read 前 → 後 | 反実仮想 $ vs 実績 $ |
|---|---:|---:|---|---|---|
