# keepalive の実運用観測 (DR-0024 導入前後、日次 stats)

DR-0024 の cache 戦略 (main = `keepalive` = 常時 1h + 55 分 refresh ping) が
実運用で効いているかを、日次 stats (`/llm-gateway/stats`) の実測で評価した。
設計の根拠と分岐点の計算は DR-0024 §3、導入前の費用構成は
`2026-09-03-prompt-cache-investigation.md` が正本。

## 判明した事実

### 効いている (main 相当のモデルで write 費用が 5 分の 1)

`claude-fable-5-1` (= main セッションが載るモデル) の導入前 2 日 / 導入後 5 日
を全 credential 合算で比べると、**read 1M トークンを維持するのに要した write 費用**が
$0.759 → $0.152 に落ちた (5.0 分の 1)。read の量はむしろ 2.6 倍に増えている
(573.9M → 1478.8M) ので、「使わなくなったから安くなった」ではない。

| | req | write | read | $write | $read | $合計 | write 比 | $/req | $write/1M read |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 導入前 (09-02〜03) | 1,259 | 34.8M | 573.9M | 435.45 | 143.47 | 604.88 | 72.0% | 0.480 | 0.759 |
| 導入後 (09-04〜08) | 3,330 | 14.9M | 1478.8M | 225.51 | 369.69 | 672.03 | 33.6% | 0.202 | 0.152 |

- **費用の支配項が write から read へ移った** (72.0% → 33.6%)。DR-0024 が狙った
  「5 分失効後の全量再構築を無くす」がそのまま数字に出ている
- リクエスト単価は $0.480 → $0.202 (2.4 分の 1)。1 リクエストあたりの read は
  308〜524k → 409〜497k とほぼ横ばいで、prefix が縮んだわけではない
- 導入後の write $225.51 を導入前の単位費用で置き換えると $1,122 相当。
  **5 日で約 $900 の削減**に見える (この換算は下記「推測」の扱い)

### 介入が main だけで足りる、が数字で裏付いた

`ephemeral_1h` / `ephemeral_5m` の内訳が取れる 09-06 以降で、モデルごとの
1h write 比率が大きく違う:

| モデル | 1h write 比率 (09-06〜08) | 解釈 |
|---|---:|---|
| `claude-fable-5-1` | 100% (2.13M/2.13M、09-08) | main が載るモデル。全て 1h 戦略下 |
| `claude-sonnet-5` | 48〜67% | main と sub が混在 |
| `claude-opus-5` | 0〜14% | ほぼ subagent (= `passthrough` の 5m) |

`opus-5` は worker 用途が支配的で、DR-0024 の「sub は passthrough」がそのまま
効いている。改善幅も main 系ほど大きくない ($write/1M read が 0.338 → 0.242、
sonnet は 0.323 → 0.204)。導入前調査の「費用の 9 割は main」と整合する。

### ping の費用は無視できる規模

- Fable 5.1 の cache read は $0.25/MTok、1 リクエストあたりの read が
  約 45 万トークンなので、**ping 1 回 ≈ $0.11**。DR-0024 の週次試算が置いた
  $0.1 と一致する
- 1h write は $20/MTok なので比は 80 倍。DR-0024 §3 の「5.1 系 80 回 ≈ 73.3 時間」
  「horizon 0.3 → 22 時間」の前提は単価表 (`preset/pricing.rs`) と一致していて、
  設定値 (`keepalive_horizon = 0.3`、personal / bare / 業務面の 3 namespace) も
  設計どおり入っている
- ただし **ping の実発火回数は残っていない** (下記「データ不足」)

### 副作用は観測範囲では出ていない

- **停止の残留なし**: 両プロセスの `GET /llm-gateway/keepalive/paused` が
  ともに空。置き場のファイルにも `paused` は 0 件。ログに残る pause は 1 セッション
  分だけで、いずれも数秒以内に実リクエストで resume されている
  (DR-0024 §2「解くのは実リクエスト 1 本だけ」が実際に働いている)
- **1h write の連発なし**: 導入後の write 総量はむしろ減っている。「マーカーが
  毎回 2 倍で書き直す」不採用案の症状 (read 数万 / write 数十万) は出ていない
- **多プロセスの重複なし**: 現時点の見張りは 11301 に 15 系列 / 11302 に 1 系列で、
  同じ `(session_id, prefix)` の重複は無い。ping 回数も 0〜5 回に収まっていて、
  55 分刻みの範囲を超えていない
- **設定漏れの検出は働いた**: 09-04 04:47Z の 1 回だけ
  `cache keepalive needs a webhook destination; no signal will be sent` が出ている。
  この起動では ping が出ていない (= 1h 戦略のみ) はずで、DR-0024 §2-6 の
  警告が意図どおり鳴った例

## 実用的な示唆 / ベストプラクティス

- **導入日は 09-04 (JST)**。keepalive の見張り復元ログの初出が 2026-09-03T17:01Z。
  日次 stats でも `fable-5-1` の read/write 比が 09-03 の 15.7 から 09-04 に 70.0 へ
  跳ねていて、境界がはっきり出る
- **`ephemeral_1h` / `ephemeral_5m` の内訳が stats に入ったのは 09-06 から**。
  09-04〜05 の 2 日は「1h が効いていたことは read/write 比から分かるが、
  内訳では確認できない」。導入前後の厳密な内訳比較をしたい場合はこの穴を意識する
- **1h write 比率はモデル単位の main/sub 混在度の指標として使える**。
  `cache_strategy` を per-request に持たなくても、日次 stats だけで
  「どのモデルが main 用途か」が読める
- 評価指標は「write 総額」でなく **`$write` ÷ read トークン量** を使うのが良い。
  稼働量が日ごとに 10 倍近く振れるので、総額では前後比較にならない

## 結論

**効いている。** ただし削減額の絶対値は推測。

- 確定: main が載るモデルで write の費用比が 72% → 34% に落ち、read 量あたりの
  write 費用が 5 分の 1 になった。read 量は増えているので稼働減が原因ではない
- 確定: 停止の残留・1h write の連発・多プロセス重複といった副作用は、
  現時点の置き場とログの範囲では観測されない
- 推測: 「5 日で約 $900 削減」は、導入前の単位費用を導入後の read 量に当てた
  外挿。実際には (a) 09-02 に `fable-5` → `fable-5-1` へ移って cache read 単価が
  1.0 → 0.25 に下がっている、(b) 導入前サンプルが 2 日しかない、(c) セッションの
  長さ・並列度が日ごとに違う、の 3 点が交絡する。桁 (数百ドル/週) は信じてよいが、
  金額そのものは幅を持って読む

### データ不足 — 決着させるなら足す計測

1. **ping の発火回数と結果の内訳**。今は置き場の `count` (生きている系列の
   現在値) しか残らず、`applied` / `late` / `foreign` の履歴が消える。
   日次 stats と同じ流儀で `<stats dir>/keepalive-counters/<待ち受け>.json` に
   日別の {出した数, applied, late, foreign, 出したが戻らなかった数} を積めば、
   ping 費用の実額と収束の健全性 (`foreign` の多さ = 重複) が両方取れる
2. **ping トークンの分離**。ping も普通の 1 本として stats に入るので、
   「ping 由来の read」と「会話由来の read」が混ざる。トークン種別に
   keepalive 印を足すか、上記カウンタに read トークン量も積めば、
   損益分岐 (horizon 0.3 の妥当性) を実測で検算できる
3. **horizon の事後評価**。「ping を出した系列のうち、実際に会話が再開したのは
   何割か」が取れると、0.3 が高すぎ / 低すぎの判断ができる。1 の履歴に
   「この系列は最終的に実リクエストで再開したか」を足すのが最小の形

## 検証の詳細

### 使ったデータ

- `GET /llm-gateway/stats?days=20` (11301)。**この口は全 writer のファイルを
  合算して返す**ことを確認済み (09-07 の 3 ファイル合計 1,732 req = 口の返り値)
- 置き場: `<state dir>/llm-gateway/stats/keepalive/<待ち受け>.json` (4 ファイル)
- ログ: 11301 の unstable ログを `sed -E 's/\x1b\[[0-9;]*m//g'` して `keepalive` で grep
  (57 行。INFO では起動時の見張り復元と pause/resume だけが出る)
- 単価: `crates/llm-gateway/src/preset/pricing.rs`
  (Fable 5.1 = input 10 / output 50 / write5m 12.5 / write1h 20 / read 0.25)

### モデル別・日別 (抜粋、全 credential 合算)

`wr%` = write が総額に占める割合。`$w/Mr` = read 1M トークンあたりの write 費用。

| 日 | モデル | req | $write | $read | $合計 | wr% | $/req |
|---|---|---:|---:|---:|---:|---:|---:|
| 09-02 | fable-5-1 | 399 | 76.33 | 30.76 | 115.87 | 65.9% | 0.290 |
| 09-03 | fable-5-1 | 860 | 359.12 | 112.71 | 489.01 | 73.4% | 0.569 |
| 09-04 | fable-5-1 | 499 | 36.48 | 51.07 | 96.52 | 37.8% | 0.193 |
| 09-05 | fable-5-1 | 514 | 52.60 | 52.09 | 113.67 | 46.3% | 0.221 |
| 09-06 | fable-5-1 | 856 | 43.30 | 105.26 | 164.44 | 26.3% | 0.192 |
| 09-07 | fable-5-1 | 493 | 50.47 | 61.26 | 126.44 | 39.9% | 0.256 |
| 09-08 | fable-5-1 | 968 | 42.66 | 100.02 | 170.96 | 25.0% | 0.177 |

read/write 比 (トークン量) の推移も同じ境界を示す:

| 日 | 09-02 | 09-03 | 09-04 | 09-05 | 09-06 | 09-07 | 09-08 |
|---|---:|---:|---:|---:|---:|---:|---:|
| fable-5-1 | 20.2 | 15.7 | 70.0 | 49.5 | 157.3 | 82.3 | 187.5 |

導入前の `fable-5` (08-20〜09-03) は 7.8〜23.4 の範囲に収まっていて、
導入後の 49.5〜187.5 とは重ならない。

### モデル別の前後まとめ

| モデル | $w/Mr 前 | $w/Mr 後 | wr% 前 → 後 |
|---|---:|---:|---|
| fable-5-1 | 0.759 | 0.152 | 72.0% → 33.6% |
| opus-5 | 0.338 | 0.242 | 37.1% → 29.7% |
| sonnet-5 | 0.323 | 0.204 | 51.0% → 39.7% |

main が支配的な fable で改善幅が突出し、sub が支配的な opus で最も小さい。
介入対象 (main) と改善幅の順序が一致している。

### 見張りの現況 (2026-09-08 時点)

11301 が 15 系列 (personal 9 / bare 4 / 業務面 2)、11302 が 1 系列。
ping 回数は 0 が 6 系列、1 が 5 系列、2 / 4 / 5 が各 1 系列。
`kind` は全て `primary` で、控え (`foreign` 経由) に回った系列は無い。

### やっていないこと

- 会話本文 (tap の `request_body`) は読んでいない。判定は全て集計値・置き場・
  ログのみ
- 稼働機の設定変更・再起動はしていない (読み取りのみ)
- セッション単位の突き合わせ (どの main セッションが何回 ping を受けたか) は、
  stats が credential × モデル × 日の粒度しか持たないため不可能
