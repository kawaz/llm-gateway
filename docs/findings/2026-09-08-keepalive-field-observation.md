# keepalive の実運用観測 (DR-0024 導入前後、日次 stats)

DR-0024 の cache 戦略 (main = `keepalive` = 常時 1h + 55 分 refresh ping) が
実運用で効いているかを、日次 stats (`/llm-gateway/stats`) の実測で評価した。
設計の根拠と分岐点の計算は DR-0024 §3、導入前の費用構成は
`2026-09-03-prompt-cache-investigation.md` が正本。

## 判明した事実

### 効いている (read 正規化で 1/5、ping 補正後は約 1/4.6、write+延命費用の項で約 1/4)

`claude-fable-5-1` (= main セッションが載るモデル) の導入前 2 日 / 導入後 5 日
を全 credential 合算で比べると、**read 1M トークンを維持するのに要した write 費用**が
$0.759 → $0.152 に落ちた (5.0 分の 1)。read の量はむしろ 2.6 倍に増えている
(573.9M → 1478.8M) ので、「使わなくなったから安くなった」ではない。

| | req | write | read | $write | $read | $合計 | write 比 | $/req | $write/1M read |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 導入前 (09-02〜03) | 1,259 | 34.8M | 573.9M | 435.45 | 143.47 | 604.88 | 72.0% | 0.480 | 0.759 |
| 導入後 (09-04〜08) | 3,330 | 14.9M | 1478.8M | 225.51 | 369.69 | 672.03 | 33.6% | 0.202 | 0.152 |

- **費用の支配項が write から read へ移った** (72.0% → 33.6%)。DR-0024 が狙った
  「5 分失効後の全量再構築を無くす」がそのまま数字に出ている
- リクエスト単価は $0.480 → $0.202 (2.4 分の 1)。1 リクエストあたりの read は
  308〜524k → 409〜497k とほぼ横ばいで、prefix が縮んだわけではない

ただし **この read には ping 自身の read が混ざっている** (ping は普通の 1 本として
stats に入る)。分母から ping を抜いて、ping 費用を延命費用として費用側に立てると:

| | 見かけ read | ping read | 実 read | $write | $ping | $write/1M 実read | $(write+ping)/1M 実read |
|---|---:|---:|---:|---:|---:|---:|---:|
| 導入前 (09-02〜03) | 573.9M | 22.5M | 551.4M | 435.45 | 5.62 | 0.7897 | 0.7999 |
| 導入後 (09-04〜08) | 1478.8M | 163.2M | 1315.6M | 225.51 | 40.80 | 0.1714 | 0.2024 |

- **ping 補正後も 4.61 分の 1** ($0.7897 → $0.1714)。ping の read は導入後 5 日で
  163.2M = 見かけ read の 11.0% で、補正しても桁は動かない
- **延命費用を費用側に立てても 3.95 分の 1** ($0.7999 → $0.2024)。ping 330 回で
  $40.80 (1 回あたり $0.124) は、消えた write の前では小さい
- 同じ実 read 1315.6M を導入前の write 率で賄うと $1,038.95。実 write $225.51 +
  ping $40.80 = $266.31 なので、**5 日で純減 $786** (ping 費用を差し引いた後)

### ping 費用が節約を食い切るモデルがある (opus-5)

同じ補正を全モデルにかけると、モデルによって結論が変わる:

| モデル | 実 read (後) | ping 回数 (後) | $ping | $w/1M実read 前 → 後 | write のみ | write+ping | 5 日の純減 |
|---|---:|---:|---:|---|---:|---:|---:|
| `claude-fable-5-1` | 1315.6M | 330 | 40.80 | 0.7897 → 0.1714 | 4.61x | **3.95x** | +$786.06 |
| `claude-opus-5` | 931.3M | 226 | 63.25 | 0.3377 → 0.2744 | 1.23x | **0.99x** | **-$4.30** |
| `claude-sonnet-5` | 664.6M | 0 | 0.00 | 0.3233 → 0.2043 | 1.58x | **1.58x** | +$79.13 |

- **`opus-5` は ping 補正後に改善が消える** (1.23x → 0.99x、純減 -$4.30 = ほぼ
  収支ゼロ、わずかに赤)。理由は 2 つ重なる: (a) opus は read 単価が input の 0.1 倍
  = 分岐比 20 倍しかないので ping 1 回が相対的に高い ($0.28/回、fable の 2.3 倍)、
  (b) opus は subagent が支配的で、少数の main 系列を延命するために払う ping が
  節約した write と釣り合ってしまう
- `sonnet-5` は ping が 1 回も観測されず、1.58 分の 1 が丸ごと残る
- **fable / sonnet の黒字が opus の収支ゼロを大きく上回る**ので、全体では黒字。
  ただし opus の `keepalive_horizon = 0.3` (= 5.5 時間) は、この 5 日を見る限り
  **短くする方向に見直す余地がある**

### 介入が main だけで足りる、が数字で裏付いた

`ephemeral_1h` / `ephemeral_5m` の内訳が取れる 09-06 以降で、モデルごとの
1h write 比率が大きく違う:

| モデル | 1h write 比率 (09-06〜08) | 解釈 |
|---|---:|---|
| `claude-fable-5-1` | 100% (2.13M/2.13M、09-08) | main が載るモデル。全て 1h 戦略下 |
| `claude-sonnet-5` | 48〜67% | main と sub が混在 |
| `claude-opus-5` | 0〜14% | ほぼ subagent (= `passthrough` の 5m) |

`opus-5` は worker 用途が支配的で、DR-0024 の「sub は passthrough」がそのまま
効いている。改善幅も main 系ほど大きくない ($write/1M read が 0.338 → 0.242、
sonnet は 0.323 → 0.204)。導入前調査の「費用の 9 割は main」と整合する。

### ping の実回数と単価 (セッション jsonl から実測)

gateway 側に発火履歴が残らないので、**セッション jsonl 側の応答から数えた**
(手順は「検証の詳細」)。導入後 5 日で 556 回・read 290M:

| 日 | 09-03 | 09-04 | 09-05 | 09-06 | 09-07 | 09-08 |
|---|---:|---:|---:|---:|---:|---:|
| ping 回数 | 35 | 107 | 198 | 146 | 69 | 36 |
| ping read | 22.5M | 41.5M | 108.3M | 79.3M | 43.6M | 16.9M |

- 観測された ping は `fable-5-1` (365 回) と `opus-5` (226 回) だけ
- **ping 1 回の実費は fable $0.124 / opus $0.280**。DR-0024 の週次試算が置いた
  $0.1 は fable では当たっている (実測はやや高い) が、**opus では 2.8 倍高い**。
  read 単価が input の 0.025 倍 (fable) と 0.1 倍 (opus) で 4 倍違うため
- 1h write は fable $20/MTok なので比は 80 倍。DR-0024 §3 の「5.1 系 80 回 ≈ 73.3 時間」
  「horizon 0.3 → 22 時間」の前提は単価表 (`preset/pricing.rs`) と一致していて、
  設定値 (`keepalive_horizon = 0.3`、personal / bare / 業務面の 3 namespace) も
  設計どおり入っている
- この回数は **下限**。数えられるのは「ping に応答してその応答が走査対象の jsonl に
  残ったもの」だけで、置き場では見張られている `sonnet-5` 系列の ping が 1 件も
  出てこないのは取りこぼしの可能性がある (下記「データ不足」)

### 副作用は観測範囲では出ていない

- **停止の残留なし**: 両プロセスの `GET /llm-gateway/keepalive/paused` が
  ともに空。置き場のファイルにも `paused` は 0 件。ログに残る pause は 1 セッション
  分だけで、いずれも数秒以内に実リクエストで resume されている
  (DR-0024 §2「解くのは実リクエスト 1 本だけ」が実際に働いている)
- **1h write の連発なし**: 導入後の write 総量はむしろ減っている。「マーカーが
  毎回 2 倍で書き直す」不採用案の症状 (read 数万 / write 数十万) は出ていない
- **多プロセスの重複なし**: 現時点の見張りは 11301 に 15 系列 / 11302 に 1 系列で、
  同じ `(session_id, prefix)` の重複は無い。ping 回数も 0〜5 回に収まっていて、
  55 分刻みの範囲を超えていない
- **設定漏れの検出は働いた**: 09-04 04:47Z の 1 回だけ
  `cache keepalive needs a webhook destination; no signal will be sent` が出ている。
  この起動では ping が出ていない (= 1h 戦略のみ) はずで、DR-0024 §2-6 の
  警告が意図どおり鳴った例

## 実用的な示唆 / ベストプラクティス

- **導入日は 09-04 (JST)**。keepalive の見張り復元ログの初出が 2026-09-03T17:01Z。
  日次 stats でも `fable-5-1` の read/write 比が 09-03 の 15.7 から 09-04 に 70.0 へ
  跳ねていて、境界がはっきり出る
- **`ephemeral_1h` / `ephemeral_5m` の内訳が stats に入ったのは 09-06 から**。
  09-04〜05 の 2 日は「1h が効いていたことは read/write 比から分かるが、
  内訳では確認できない」。導入前後の厳密な内訳比較をしたい場合はこの穴を意識する
- **1h write 比率はモデル単位の main/sub 混在度の指標として使える**。
  `cache_strategy` を per-request に持たなくても、日次 stats だけで
  「どのモデルが main 用途か」が読める
- 評価指標は「write 総額」でなく **`$write` ÷ (read − ping read)** を使う。
  稼働量が日ごとに 10 倍近く振れるので総額では前後比較にならず、かつ ping 自身の
  read が分母を 11% 水増しするので、ping を抜かないと改善を過大評価する
- **ping 費用はモデル単位で評価する**。read 単価が input の 0.025 倍 (5.1 系) か
  0.1 倍 (それ以外) かで ping 1 回の実費が 4 倍違い、5.1 系で成立する
  `keepalive_horizon = 0.3` が他モデルでは収支ゼロになりうる

## 結論

**効いている (ping 補正後も)。** ただしモデルによって収支が違い、削減額の絶対値は推測。

- 確定: main が載るモデル (`fable-5-1`) で write の費用比が 72% → 34% に落ちた。
  ping の read を分母から抜いても実 read 1M あたりの write 費用は
  $0.7897 → $0.1714 (4.61 分の 1)、ping 費用を費用側に立てても
  $0.7999 → $0.2024 (3.95 分の 1)。read 量は増えているので稼働減が原因ではない
- 確定: **`opus-5` では ping 費用が節約を食い切る** (write のみ 1.23x →
  write+ping 0.99x、5 日で純減 -$4.30)。全体では fable / sonnet の黒字が
  これを大きく上回るので黒字だが、opus の horizon は見直し候補
- 確定: 停止の残留・1h write の連発・多プロセス重複といった副作用は、
  現時点の置き場とログの範囲では観測されない
- 推測: 「5 日で純減 $786 (fable)」は、導入前の単位費用を導入後の実 read 量に
  当てた外挿。次の 3 点が交絡する:
  1. **ping 回数はモデル別に割れたが下限**。`sonnet-5` は見張られている系列が
     あるのに ping が 1 件も観測されず、走査対象の jsonl の外に落ちている疑いがある
  2. **導入前 2 日のうち 09-03 に既に 35 ping が出ている** (導入日は 09-04 だが
     見張り自体は 09-03T17:01Z から動いていた)。導入前の基準値も純粋ではない
  3. **単価が 5.1 系のもの**。09-02 に `fable-5` → `fable-5-1` へ移って cache read
     単価が 1.0 → 0.25 に下がっており、導入前サンプル 2 日はこの移行直後に当たる。
     加えてセッションの長さ・並列度が日ごとに違う

  桁 (数百ドル/週) は信じてよいが、金額そのものは幅を持って読む

### データ不足 — 決着させるなら足す計測

1. **ping の発火回数と結果の内訳**。回数と read は jsonl 側から拾えたが、これは
   「応答が jsonl に残ったもの」の下限で、gateway が出した数ではない。また
   `applied` / `late` / `foreign` の別が取れないので、期限内に間に合ったのか
   (`late` = cache が消えてから届いた = 払い損) が分からない。
   日次 stats と同じ流儀で `<stats dir>/keepalive-counters/<待ち受け>.json` に
   日別の {出した数, applied, late, foreign, 出したが戻らなかった数, read トークン}
   を積めば、ping 費用の実額と収束の健全性 (`foreign` の多さ = 重複) が両方取れて、
   jsonl 走査という外部依存も要らなくなる
2. **ping トークンを stats 側で分離する**。ping も普通の 1 本として stats に入るため、
   今回は jsonl から数えた ping read を手で引いている。トークン種別に keepalive 印を
   足せば、`$write ÷ 実 read` が stats だけで出せる
3. **horizon の事後評価**。「ping を出した系列のうち、実際に会話が再開したのは
   何割か」が取れると、0.3 が高すぎ / 低すぎの判断ができる。1 の履歴に
   「この系列は最終的に実リクエストで再開したか」を足すのが最小の形。
   **`opus-5` の収支ゼロを踏まえると、これは最優先**: 再開率が分かれば
   「5.1 系以外は horizon を下げる」の判断が数字でできる

### 使ったデータ

  合算して返す**ことを確認済み (09-07 の 3 ファイル合計 1,732 req = 口の返り値)
- 置き場: `<state dir>/llm-gateway/stats/keepalive/<待ち受け>.json` (4 ファイル)
- ログ: 11301 の unstable ログを `sed -E 's/\x1b\[[0-9;]*m//g'` して `keepalive` で grep
  (57 行。INFO では起動時の見張り復元と pause/resume だけが出る)
- 単価: `crates/llm-gateway/src/preset/pricing.rs`
  (Fable 5.1 = input 10 / output 50 / write5m 12.5 / write1h 20 / read 0.25、
  Opus 5 = 5 / 25 / 6.25 / 10 / 0.5、Sonnet 5 = 3 / 15 / 3.75 / 6 / 0.3)
- ping の回数と read: **セッション jsonl 側から実測** (gateway に発火履歴が無いため)

### ping の数え方 (jsonl 走査)

`~/.claude*/projects/*/*.jsonl` を走査 (3,635 ファイル)。各行を JSON として読み、
`type == "assistant"` かつ content の text ブロックに合言葉 `LLMGW-KEEPALIVE-` を
含むものを `(timestamp[:10], message.id)` でユニーク化して数え、
`message.usage.cache_read_input_tokens` を合算する。`message.model` でモデル別に割った。

**ユニーク化は必須** — streaming 途中の中間値で同じ `message.id` の行が複数回出る
(導入前調査の「dedupe して最後の値を採る」と同じ罠)。

数えているのは「**ping に応答した assistant メッセージ**」なので、gateway が出した
本数ではなく**下限**になる。応答しなかった / 走査対象外の設定ディレクトリに
落ちた分は数えられない。

| 日 | モデル | ping 回数 | ping read |
|---|---|---:|---:|
| 09-03 | fable-5-1 | 35 | 22.5M |
| 09-04 | fable-5-1 / opus-5 | 85 / 22 | 33.1M / 8.4M |
| 09-05 | fable-5-1 / opus-5 | 77 / 121 | 38.1M / 70.2M |
| 09-06 | fable-5-1 / opus-5 | 75 / 71 | 37.9M / 41.4M |
| 09-07 | fable-5-1 | 69 | 43.6M |
| 09-08 | fable-5-1 / opus-5 | 24 / 12 | 10.5M / 6.5M |

導入後 5 日の合計は 556 回 / 290.0M (fable 330 回 163.2M、opus 226 回 126.5M)。
`sonnet-5` は 0 件 — 置き場では sonnet の系列が 7 本見張られているので、
取りこぼしを疑う根拠になる。

### ping 補正の計算

実 read = 見かけ read − ping read、ping 費用 = ping read × cache read 単価。
導入前の単位費用 (`$write ÷ 実 read`) を導入後の実 read に当てたものを反実仮想とする。

| モデル | 実read 前 | 実read 後 | $w/M実read 前 → 後 | $(w+ping)/M実read 前 → 後 | 反実仮想 $ vs 実績 $ |
|---|---:|---:|---|---|---|
| fable-5-1 | 551.4M | 1315.6M | 0.7897 → 0.1714 (4.61x) | 0.7999 → 0.2024 (3.95x) | 1052.37 vs 266.31 |
| opus-5 | 494.9M | 931.3M | 0.3377 → 0.2744 (1.23x) | 0.3377 → 0.3423 (**0.99x**) | 314.49 vs 318.79 |
| sonnet-5 | 413.1M | 664.6M | 0.3233 → 0.2043 (1.58x) | 同左 (ping 0) | 214.89 vs 135.76 |

ping を**全モデル合算のまま fable の read から引く**と 3.03x になるが、これは
opus の ping 126.5M を fable から差し引く過剰控除で、モデル別に割った 3.95x が正しい。

### モデル別の前後まとめ

| モデル | $w/Mr 前 | $w/Mr 後 | wr% 前 → 後 |
|---|---:|---:|---|
| fable-5-1 | 0.759 | 0.152 | 72.0% → 33.6% |
| opus-5 | 0.338 | 0.242 | 37.1% → 29.7% |
| sonnet-5 | 0.323 | 0.204 | 51.0% → 39.7% |

main が支配的な fable で改善幅が突出し、sub が支配的な opus で最も小さい。
介入対象 (main) と改善幅の順序が一致している。ping 補正を掛けると opus の
改善は 0.99x まで縮んで消える (上記「ping 補正の計算」)。

### 見張りの現況 (2026-09-08 時点)

11301 が 15 系列 (personal 9 / bare 4 / 業務面 2)、11302 が 1 系列。

### やっていないこと

- 会話本文 (tap の `request_body`) は読んでいない。判定は全て集計値・置き場・
  ログと、jsonl の「合言葉を含むか / usage / model / message.id」だけ
  (本文そのものは読んでいない)
- 稼働機の設定変更・再起動はしていない (読み取りのみ)
- セッション単位の突き合わせ (どの main セッションが何回 ping を受けたか) は、
  stats が credential × モデル × 日の粒度しか持たないため不可能
